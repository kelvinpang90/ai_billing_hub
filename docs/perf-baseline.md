# 容量基线 — Phase 0（T0.10）

> spec §119 给的那组 V1 工程验收目标写明是「**to be validated and adjusted through a
> documented Phase 0 capacity baseline**」。这份文件就是那个基线。
>
> 测量工具：[`scripts/perf_baseline.py`](../scripts/perf_baseline.py)，可重复跑。
> 最后一次测量：2026-09-12（开发机）、**2026-09-17（生产 VPS，见第 9 节）**。
> Phase 2 的最热租户压测（用量计费 S1–S4）用 [`scripts/perf_usage.py`](../scripts/perf_usage.py)，见第 10 节（结果待运维回填）。

## 0. 先说这份基线**不是**什么

⚠️ **它没有验证 §119 里那几条目标。**那几条说的是用量事件的摄取与钱包变更 ——
两者在 Phase 0 都还不存在（用量表 Phase 2，钱包表 Phase 1）。凭空造一个假的用量
事件去量，得到的是一个**看起来像基线的数字**，而它与将来那条真实路径没有关系。
那比没有基线更糟：它会被人当成结论引用。

所以下面只量**现在真实存在、且将来仍在关键路径上**的东西，并在第 5 节逐条写清楚
§119 的哪些目标还欠着、要等哪个 Phase 才量得了。

⚠️ **这些数字来自开发机，不是生产 VPS。**外推到生产之前必须在目标机器上重跑一次
（命令在第 6 节）。绝对值一定会变；**形状**（哪里饱和、哪里出现尾部）大概率不变。

## 3. 读出来的五件事

### 3.1 ⚠️ 每一条路径都在**并发 8** 饱和，而机器有 20 核

写入路径 390/s 出现在并发 8；16 与 32 反而掉到 ~375/s，延迟却从 20ms 涨到 39ms、
p99 从 37ms 炸到 **1665ms**。`/healthz` 同样：并发 8 已经 1070/s，并发 32 还是
1097/s，只是每个请求多等 21ms。

**多出来的并发全部变成排队，没有一点变成吞吐。**

原因不在数据库，在于 **API 是单个 uvicorn 进程**（`Dockerfile` 的 CMD 里没有
`--workers`）。所有非 C 扩展的工作都在一个 GIL 后面排队，加机器核数不会有任何帮助。

> **这条归 T0.9。**改进程模型是部署拓扑决策，不在一个测量任务的范围里。
> ⚠️ 而且它**不是一个免费的性能开关**：见 3.4。

### 3.2 登录的成本是 35ms CPU + 64 MiB 内存，每一次

Argon2id 校验 p50 **35.9ms**，参数是 argon2-cffi 的默认值
（`time_cost=3`、`memory_cost=65536 KiB = 64 MiB`、`parallelism=4`）。

两条推论：

- **CPU**：单线程约 **28 次/秒**。Argon2 在 C 层会释放 GIL，所以它是少数能吃到
  多核的部分
- **内存**：每一次并发的哈希要 **64 MiB**。20 个并发登录 = **1.28 GB**。
  单 VPS 上这是个硬约束，和 CPU 一样值钱

⚠️ **这一项只量、不调。**Argon2 的参数是认证与会话的安全参数（设计闸门 #32 的
范畴）。在一个性能任务里顺手调低它，是把一次安全决策伪装成性能优化。

### 3.3 认证端点的真实上限是限流器，不是 Argon2

两层限流都配着 **10 r/m、突发 20**：边缘 nginx 的 `limit_req`（主控，
`deploy/nginx/billing.conf:38`）与进程内的 `TokenBucket`（兜底）。

所以**按来源**看，登录的稳态上限是 10/分钟 —— 远在 3.2 那个 28/秒之下。Argon2 的
开销要到「大量不同来源同时登录」时才会变成瓶颈。

⚠️ **认证端点刻意没有做 HTTP 压测。**打到第 21 个请求就是 429，压出来的是限流器
的形状而不是服务的容量。**而为压测加一个「关掉限流」的开关是不行的** —— 那种开关
一旦存在，早晚有人在生产上打开（与 ADR-0009 拒绝「允许明文 SMTP」开关同一个理由）。
所以 Argon2 在进程内量。

### 3.4 ⚠️ 「加 `--workers`」会让**兜底**限流按 worker 数放大

进程内的 `TokenBucket` 状态在进程内存里（理由见 `app/core/ratelimit.py`：放 Redis
会 fail-open，而一个丢了就失效的安全控制比没有更危险）。跑 N 个 worker，同一个来源
就有 N 个独立的桶 —— **兜底层的有效额度变成 N 倍**。

主控那层（nginx）不受影响，所以这不是阻断项；但 T0.9 在调进程模型时必须知道
「兜底被削弱了多少」，而不是事后才发现。

### 3.5 反枚举的耗时地板让忘记密码的吞吐降到 8.3/s（每进程）

真实写入只要 5.8ms，而端点固定耗时 120ms（T0.8d 的反用户枚举控制）。差额是
`time.sleep`，不吃 CPU，但**占着线程池的一个线程**。

单进程下 FastAPI 的同步线程池默认 40 个线程 → 忘记密码端点的理论上限约
**333/s**，与限流的 10 r/m 相比绰绰有余。**记在这里是为了将来别把它当成谜题**：
这个端点的 p50 永远是 120ms，那是设计，不是慢。

## 4. 这次基线导致的改动

| 改动 | 依据 |
| --- | --- |
| 连接池三个参数变成配置项（`database_pool_size` / `_max_overflow` / `_timeout_seconds`） | T0.4 欠着这件事，写明「等 T0.10 有了并发基线」 |
| **池大小默认值不变**（5 + 10） | 3.1：并发 8 就饱和，池再大也只是让更多请求一起排队 |
| **`pool_timeout` 从 SQLAlchemy 默认的 30 秒改成 5 秒** | 池满时干等 30 秒对 HTTP 接口毫无意义 —— 调用方早就超时，我们还占着线程和连接。**这是这次唯一改了行为的值** |
| 前端路由级懒加载 | 见第 7 节。⚠️ 收益比预期小得多，数字照实记 |

## 5. §119 的目标：哪些还量不了

| §119 的目标 | 现在能不能量 | 为什么 |
| --- | --- | --- |
| Stored Usage Events >= 1,000,000 | ❌ | 用量表 Phase 2 才建 |
| Sustained ingestion >= 20 events/s | ❌ | 同上。⚠️ 但 S2 的 390/s 说明**写入路径本身**离 20/s 很远，不是风险点 |
| Five-minute burst >= 100 events/s | ❌ | 同上 |
| Durable-acceptance API latency p95 <= 500ms | ⚠️ 部分 | S2 是形状最接近的写入路径：并发 8 时 p95 25ms。但真实摄取还要加鉴权、配额与定价 |
| Event-to-wallet p95 <= 60s / p99 <= 5min | ❌ | 钱包 Phase 1、计费引擎 Phase 2 |
| Backlog recovery >= 5x peak | ⚠️ 部分 | S3 量的正是将来承载它的那套 outbox 机制：单线程 98.4/s。⚠️ 恢复扫描现在是**单个 beat 任务串行投递**，5x 目标真到跟前时要重新量 |
| Status Webhook first delivery attempt p95 <= 60s | ❌ | Webhook 是 Phase 3 |
| 99.5% 月度可用性 | ❌ | 要生产环境跑满一个月才谈得上 |
| **最热租户的工作负载** | ❌ | `users` 表现在还没有 `tenant_id`（Phase 4 引入 CUSTOMER 时才有） |

⚠️ spec §119 还要求「**最热租户**的工作负载必须包含在测量里，因为钱包变更是按租户
串行的」。那一条**在 Phase 1 建出钱包表之前无法满足**，必须在 Phase 1 的容量测量里
补上 —— 它恰恰是最容易被漏掉的那一条，因为平均负载看起来一直很健康。

> 用量摄取与计费在 Phase 2 落地之后，事件到扣费、回补速率与最热租户这三行由第 10 节的
> S1–S4 来量。

## 6. 怎么重跑

### ⚠️ 测量必须用一个**独立的 schema**，不能用栈自己那个库

S2 会写出上千行状态为 `PENDING`、payload 里带着**真实重置令牌**的 outbox 行。而
compose 里的 celery-beat 每 60 秒跑一次恢复扫描，worker 会在**它自己的进程**里投递
它们 —— 脚本里那个 `NullTransport` 只换掉了脚本自己进程的传输层，对 worker 毫无作用。

本地栈刻意不配 SMTP，所以这件事在本地看不见；**配了 SMTP 的环境会真的把上千封带
令牌的信发出去**。所以 `--database-url` 是必填的（不回落到 `BILLING_DATABASE_URL`），
而且有**两道**互不依赖的拒绝：

| 守卫 | 挡什么 | 挡不住什么 |
| --- | --- | --- |
| URL 归一化比对（host / port / database） | 「写法不同、目标相同」，例如去掉 `?charset=utf8mb4`、改大小写、省略默认端口、换凭据 | 同一台机器的不同主机名写法 |
| 连上之后问服务器（`@@server_uuid` + `DATABASE()`） | 上面那一格漏掉的全部 —— 服务器自己说了算 | 栈的库连不上时放行（那时本来也没有 worker 在跑） |

⚠️ 第二道不是第一道的重复。**URL 比对永远追不上所有等价写法**，能给出确定答案的
只有服务器本身；而第一道的价值是**不用连库就能拦下**，连不上时也仍然生效。

⚠️ `scripts/` 不在镜像里（`Dockerfile` 只 COPY 了 `app` 与 `alembic`），也要挂进去：

```bash
docker compose up -d --build
docker compose run --rm api alembic upgrade head        # 栈自己的库

# 测量专用 schema：同一个 MySQL 实例（性能特征一致），但**没有 worker 挂在上面**
PERF_URL='mysql+pymysql://root:<BILLING_MYSQL_ROOT_PASSWORD>@mysql:3306/billing_perf?charset=utf8mb4'
docker compose exec -T mysql mysql -u root -p"$BILLING_MYSQL_ROOT_PASSWORD" \
  -e 'CREATE DATABASE IF NOT EXISTS billing_perf'
docker compose run --rm -e BILLING_DATABASE_URL="$PERF_URL" api alembic upgrade head

docker compose run --rm \
  -v "$PWD/scripts:/srv/billing/scripts:ro" \
  api python scripts/perf_baseline.py --database-url "$PERF_URL"
```

跑完把 schema 删掉即可：`DROP DATABASE billing_perf`。

脚本还会：往库里写垃圾行但**跑完自己删掉**、**拒绝在
`BILLING_ENVIRONMENT=production` 下运行**、**每轮用一个唯一的账号地址并拒绝复用
已存在的账号**（它清理时会连审计记录一起删，复用别人的账号等于销毁它的审计轨迹）。

⚠️ 脚本里有一道 `_assert_writes_rows` 守卫：S2 开跑前先确认它真的写了行。这道守卫
不是防御性编程，是被一个真实缺陷逼出来的 —— 见第 8 节。

## 7. 前端首屏

| | 改前 | 改后 | 差 |
| --- | ---: | ---: | ---: |
| 分片数 | 1 | 13 | |
| 单个最大分片 | 974.50 kB | 343.14 kB | |
| **打开 `/login` 实际传输** | 974.50 kB | **934.72 kB** | **−39.78 kB（−4.1%）** |
| 同上，gzip | 316.69 kB | 约 310 kB | **约 −2%** |

⚠️ **错误边界差点把这点收益全吃掉。**懒加载引入了一个新的失败模式（分片 404 →
白屏，见 `RouteErrorBoundary.tsx`），必须加边界；而边界在**首屏**依赖图里，第一版
用了 antd 的 `Result`，那 35 kB 就从按需分片挪进了入口分片 —— `/login` 首屏从
933.91 反弹到 **968.79 kB**，省下的 40 kB 去了 34 kB。

改成只用原生元素之后回到 934.72 kB。**这件事本身也说明了这一节的结论**：在这个
前端里，首屏大小几乎完全由「有多少 antd 进了入口依赖图」决定，和拆不拆路由关系不大。

「实际传输」是在浏览器里读网络请求数到的，不是拿分片表加出来的：`/login` 真正拉了
8 个分片（`index` / `rolldown-runtime` / `button` / `client` / `auth` / `LoginPage` /
`typography` / `ErrorAlert`），没拉 `result`（34 kB）、`DashboardPage`（9 kB）与另外
三个页面片。

⚠️ **合计反而变大了**（+7.5 kB 的分片开销），这是预期内的。路由级懒加载的收益**不在
「少下载几个页面」**：五个页面的自有代码加起来才 41 kB，而 antd 占了 900 kB 以上，
且每条路由都用它 —— 它只会被提成共享分片，首屏照样要下。

**结论照实写：线上真正省下的是约 2%，这一步的价值主要在结构，不在当下的数字。**
TODO 里那条「加到第三、四个路由时必须做路由级懒加载」隐含的预期是「首屏会明显变
轻」，实测**不成立** —— 记在这里，免得下次有人照着那句话再期待一次。

结构上的收益是真的：Phase 1–4 每加一个重型 feature（图表、表格、导出）都会各自成片
而不是并进首屏。真要压首屏得从 antd 本身下手（按需引入 / 换轻量组件 / 自建主题），
那是另一个任务，已记进 TODO。

## 8. 这次测量自己踩的坑

**第一版 S2 报出 p50 = 0.02ms** —— 三张表插入加一次提交不可能这么快。原因：基线账号
用的地址是 `perf-baseline@example.invalid`，而 `normalise_email` 拒绝 `.invalid`
这个保留 TLD，于是 `_start_reset` **在第一个分支就返回、一行都没写**。

脚本照样算出了一组漂亮的百分位数，还带着可信的小数点。**一个测量了空气的自信数字
比没有基线更糟**：它会被人引用，而没有任何地方会报错。

所以现在脚本里有 `_assert_writes_rows`：S2 开跑前先跑一次、数一下行数，没写就直接
失败。**同一类守卫值得在每个测量场景里都有** —— 测量代码没有「测试」这一层兜底，
它唯一的自检就是「我量的东西真的发生了吗」。

## 9. 在生产 VPS 上重跑（2026-09-17，T0.9）

第 0 节说过：开发机的数字**不能**直接外推到生产。这一节就是那次重跑 ——
机器是升配后的生产 VPS（**2 核 / 7.4 GB**，同机还跑着另外八个项目），跑了**两轮**：
第一轮用当时的限额做对照，第二轮调高限额再量一次。

### 9.1 怎么在生产上跑、又不碰生产数据

Kelvin 同意在生产 MySQL 上**临时**建一个 `billing_perf` 再删掉。做法：

| 顾虑 | 怎么化解 |
| --- | --- |
| 写入垃圾行 | 只写 `billing_perf`。脚本自己的两道守卫（URL 比对 + 连上后问 `server_uuid` 与 `DATABASE()`）确认它**不是**栈的库；跑完 `dataset_after_run` 四类行数都是 0，库随后 `DROP` |
| 真实重置令牌被 worker 发出去 | `billing_perf` 上**没有 worker**。脚本的「拒绝在 `BILLING_ENVIRONMENT=production` 下运行」挡的就是这件事，所以只对那一个一次性容器临时把环境改成 `local`，脚本本身不改 |
| 写入进 binlog、被推到 R2 | 会进，但 `restore.sh` 重放时用 `--database` 只放行生产库 —— 恢复与每周演练都不受影响，只是多几 MB binlog |
| 同机其它项目被拖慢 | Kelvin 确认那些项目不重要 |

⚠️ 包装脚本踩了两个坑，记下来免得下次再踩：

1. **经 `ssh … bash -s < 脚本` 喂进去时，`docker compose exec` 会吞掉 stdin**，把脚本剩下的内容读走 ——
   bash 读到 EOF 正常结束、`trap` 把库删了，什么报错都没有。每条 docker 命令都要带 `</dev/null`
2. **测量库地址不能塞进 `BILLING_DATABASE_URL`**：脚本拿它和 `--database-url` 比对，一样就拒绝
   （保护按设计起作用）。测量地址要走单独的变量

### 9.2 结果

延迟单位毫秒。三列：开发机（第 2 节）、生产 · 当时的限额、生产 · 调高后的限额。

| 场景 | 开发机（20 核） | 生产 · api **0.5 核** / mysql 0.6 核 | 生产 · api **1.0 核** / mysql 0.8 核 |
| --- | ---: | ---: | ---: |
| S1a Argon2id hash · p50 | 35.1 | **592.6** | 273.7 |

### 9.3 读出来的四件事

**① 当时的限额（api 0.5 核）是这台机器上最大的瓶颈，而且没人知道。**
那两个数是按升配**之前**的 1 核机器定的，升到 2 核之后一直没调。一次登录从开发机的 35 ms
变成 **~600 ms**、每秒最多 1.7 次 —— 同时有两三个人登录，这个单进程就会把别的请求一起拖慢。

**② 调到 1 核之后几乎所有路径都回来了**：写路径峰值从 ~130/s 回到 **308/s**（开发机的 79%），
低并发时的 p95 尖刺（75 ms）消失，`/healthz` 从 ~415/s 到 ~674/s。

**③ ⚠️ Argon2 仍然慢了 8 倍（279 ms vs 35 ms），原因不只是 CPU 慢。**
argon2-cffi 默认 `parallelism=4`：四个线程**同时**烧 CPU，1.0 核的 CFS 配额（每 100 ms 周期
100 ms CPU）在墙钟 25 ms 就烧完，剩下的时间被节流。也就是说**这组参数与容器的 CPU 配额不匹配**。
要么把 api 的配额给到接近 `parallelism` 的核数，要么把 `parallelism` 调低 —— 后者是认证参数，
**要过设计闸门**，已记进 [TODO](TODO.md)，不在这次改。

**④ 「保持单进程」的结论在 2 核机器上仍然成立（决策 ②A 复核通过）。**
- 形状没变：写路径在**并发 8** 之后吞吐不再涨、尾部炸开，与开发机一致
- 更关键的是：**只要 api 的 CPU 配额 ≤ 1 核，加 `--workers` 就不可能提高吞吐** —— 多个进程分的是
  同一份配额，只会多占一倍内存、并把兜底限流额度翻倍（第 3.4 节）
- 现阶段的流量是「只有管理员」，308/s 的写路径离需要多进程还很远。**重新评估的触发条件**：
  Phase 2 的用量摄取上线、§119 的目标能真正量的时候

## 10. Phase 2：最热租户压测与用量计费（AIH-TASK-033，ADR-0011）

ADR-0011 要求用量扣费带一次最热租户压测，以及不达标时切到「同租户批事务」（方案 C）的判据。
场景、通过线与判据由 [AIH-TASK-032 的设计](design/AIH-TASK-032-usage-billing.md) §2「最热租户」
写定，下面逐字照抄；测量工具是 [`scripts/perf_usage.py`](../scripts/perf_usage.py)。

第一轮实测于 2026-10-09 在生产 VPS 上对 `billing_perf` 执行（10.4），结果与方案 C 的结论见 10.5。

### 10.1 场景与通过线（设计 §2 原文）

| 场景 | 负载 | 通过线 |
| --- | --- | --- |
| S1 突发 | 单个租户，100 事件 / 秒持续 5 分钟（§119 突发），同时 3 个其他租户各 5 事件 / 秒 | 事件到扣费延迟 p95 ≤ 60 秒、p99 ≤ 5 分钟（§119）；报告 p50 / p95 / p99 |
| S2 回补 | 单个租户预先积压 30 000 条 `RECEIVED` | 清空速率 ≥ 500 事件 / 秒（§119「≥ 峰值 5 倍」） |
| S3 崩溃与重试 | S1 进行中随机杀掉 worker 进程 3 次、注入 1% 的意外异常 | 结束后：`PROCESSED` 事件数 = 账本 `AI_USAGE` 行数（不含 0 元事件）；每个租户 `期初余额 − Σ billable_cost = 期末余额`；`verify_wallet` 全部通过；无 `LEDGER_CONFLICT` |
| S4 与发布并发 | S1 进行中每 10 秒发布一次价格 / 规则 / 汇率 | S1 的通过线仍满足；发布请求 p95 ≤ 5 秒；抽样事件用快照重算（T-G `reprice_from_snapshot`）与快照一致 |

### 10.2 方案 C 的切换判据（设计 §2 原文）

> S1 的 p95 或 p99 不达标、或 S2 的清空速率 < 500 / 秒，**且**瓶颈经测量是同一钱包行锁上的串行提交（最热租户的单事件事务平均持锁时间 × 目标速率 > 1 秒 / 秒）—— 则另开任务实现方案 C（同租户 N 个事件一个事务，每事件仍一行账本），另过设计闸门。若瓶颈在别处（例如数据库整体吞吐、worker 数量），先调那一处，不切方案 C。

脚本怎么算这两个条件：

| 条件 | 脚本的做法 |
| --- | --- |
| S1 不达标 | 全部 S1 事件（最热租户 + 其他租户）的延迟 p95 > 60 秒或 p99 > 300 秒；最热租户自己的 p50 / p95 / p99 另行报告 |
| S2 不达标 | 清空速率 = 积压条数 ÷（第一次 Beat 派发 → 最后一条的处理事务提交）< 500 / 秒 |
| 平均持锁时间 | worker 进程里给 `_lock_wallet` 包一层只记时刻的包装：钱包行锁拿到的那一刻 → `process_event` 返回（处理事务已提交）。只统计最热租户、只统计 `PROCESSED` 的事件 |
| 目标速率 | S1 用最热租户的速率（100 / 秒），S2 用 500 / 秒；哪个场景不达标就用哪个场景的速率去乘 |
| 结论 | 「需要方案 C」：至少一个不达标的场景是锁瓶颈；「不需要方案 C」：都达标，或不达标但乘积 ≤ 1（瓶颈在别处）；「无法判定」：场景无效（见下）或没量到持锁时间 |

⚠️ 场景结论有四种：`PASS`、`FAIL`、`INVALID`、`NOT_RUN`。**`INVALID` 不是失败，是「这一轮量的不是设计说的那个负载」**：
摄取的实际速率低于目标的 95%、有事件停在 `PRICING_ERROR` 之类的错误状态（造的价格 / 规则 / 汇率不对）、
S2 没造够积压、S3 没杀够次数、S4 一次发布或重算都没做成。`INVALID` 的场景不参与方案 C 的判定。
S3 在设计的四条之外还要求「事件都走完了」：核对一个还在处理中的中间态没有意义。脚本只要有一个场景是
`FAIL` 或 `INVALID` 就以退出码 1 结束。

### 10.3 脚本怎么产生负载

| 环节 | 做法 |
| --- | --- |
| 造数据 | 每轮一个唯一前缀 `perf-usage-<10 位十六进制>`。ADMIN 账号（口令随机、不保存）、供应商、每个场景一个模型、每个场景自己的客户 / 项目 / 集成凭据，全部经对应的服务函数建立；充值走管理员调账（期初余额 1 000 000 MYR，虚构） |
| 价格、规则、汇率 | 在 `billing_perf` 里按虚构值发布：USD 价格（每 1 000 token）、`GLOBAL_PROVIDER_MODEL` 范围的 MARKUP 规则（只挂在本场景的模型上）、USD→MYR 汇率。⚠️ 汇率是全局的，会截断 `billing_perf` 里上一轮留下的 USD 版本 |
| 摄取 | 经 AIH-TASK-029 的 `ingest_one`（UUIDv7 的 `event_id`、`LLM_TOKEN`），按时间表在一个线程池里发；跳过的只有 HTTP 层的验签与 nonce。**不直接写** `usage_events` |
| 计费 | `--workers` 个**子进程**（默认 2，等于 compose 的 `BILLING_CELERY_CONCURRENCY`），由主进程的一个线程按 Beat 的节奏派任务：每 10 秒一次扫描（9 秒过期）、每 60 秒一次卡住回收（54 秒过期），数值取自 `app/core/celery_app.py`。扫描循环与 `bill_pending_events` 相同（8 秒预算、每批 20 条），逐条调用 AIH-TASK-032 的 `claim_events` / `process_event`；回收调用 `recover_stale_processing`。**不直接写**账本或余额 |
| S3 的崩溃 | 在负载的 10%–90% 之间随机挑 3 个时刻，对随机一个 worker 进程发 SIGKILL，随即补一个新进程 |
| S3 的意外异常 | 每条事件以 1% 的概率换一个「第一次调用就抛异常」的时钟：异常落在处理事务中途（三把共享锁之后、扣费之前），事务回滚、按 `FAILED_RETRYABLE` + 退避记一次 |
| S4 的发布 | 负载期间每 10 秒依次发布一次价格、规则、汇率（数值交替，让快照重算有区分度），只计**发布**那一次调用的耗时；结束后抽 200 条已处理事件做 `reprice_from_snapshot`，与快照逐列比对 |
| 延迟 | `ingest_one` 返回（已提交）→ `process_event` 返回 PROCESSED（已提交），两端都是墙钟；结果没来得及回报的事件退回用库里的 `processed_at − received_at`（整秒）；没走到 `PROCESSED` 的记作无穷大 |

**按库里的时间戳复核（2026-10-10）**

脚本报告里各场景的「已处理」数加起来对不上库里的 `PROCESSED` 总数。原因是**场景之间没有隔离**：
- 每个场景只等 `--drain-timeout`（900 秒），没清空就开始下一个；
- 计费 worker 认领事件不分租户、按接收先后处理，前一个场景剩下的积压会占掉后一个场景的时间。

| 场景 | 事件数 | 接收时段（UTC） | 处理时段（UTC） | 处理结果 |
| --- | --- | --- | --- | --- |
| S1 | 34 500 | 16:00:25–16:05:25 | 16:00:34–16:27:48 | 全部 `PROCESSED`，约 21.1 条每秒（34 500 ÷ 1 634 秒） |
| S2 | 30 000 | 16:20:37–16:22:06（S1 还在处理时就灌入） | 16:27:48–16:51:45 | 全部 `PROCESSED`，约 20.9 条每秒 |

主要是吞吐远低于负载的结果；S2、S3、S4 的数字还叠加了前面场景积压的影响，单独看都偏差。

**为什么不按脚本的结论直接切方案 C**

脚本的判据是「平均持锁 × **目标**速率 > 1」，它说的是「如果要达到目标速率，锁会不会成为上限」。
但这一轮**实际**只处理了约 21 条每秒（上面的复核），钱包锁的实际占用约为 8.79 ms × 21 / 秒 ≈ 18%：锁远没有饱和。
2 个 worker 合计每秒处理约 21 条，即每条事件在一个 worker 上约 95 ms，其中持锁只占 9–10 ms，
大部分时间花在锁外。设计原文（10.2）写的是：瓶颈在别处时，先调那一处，不切方案 C。

但方案 C 不能就此排除：锁外的开销即使全部消掉，单租户串行提交的上限也只有约 1 / 8.79 ms ≈ 114 条每秒，
达不到 S2 的 500 条每秒。所以顺序是：先找出锁外约 85 ms 花在哪（数据库往返次数、MySQL 0.8 核、
一次性容器 1 核配额的节流，都是候选），调掉之后重测；重测后锁真的饱和了，再开方案 C 的设计闸门。
