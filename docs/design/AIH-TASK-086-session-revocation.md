## 1. 目标与边界

**要解决的问题**

现在改密码不会让旧会话失效：
- `reset_password` 只吊销该用户的刷新令牌（`app/services/password_reset.py`）
- 访问令牌（600 秒）和 pending 令牌（登录第二步 120 秒、注册 2FA 600 秒）是自包含的 JWT，有效期内照样能用
- 登录时读用户和密码哈希不加锁（`app/services/auth.py` 的 `authenticate`）。所以就算吊销了已有的刷新令牌，一个在重置提交前用旧密码通过校验的登录，仍会在重置之后签出一套全新的令牌和刷新令牌行

后果：知道旧密码的人，在主人改密码之后最多还能使用 10 分钟；并能在这段时间里注册自己的 2FA 验证器或重新生成恢复码，把主人锁在门外。

客户门户认证（设计闸门 #368）新增了客户自助开启 2FA 和接受邀请设置密码两条路径，这个缺口因此必须先补上。#368 的 v2 到 v5 尝试在那份设计里用「改密时刻 vs 令牌签发时刻」打补丁，每一轮审查都指出新的并发缝；Kelvin 2026-10-19 决定把它拆成本前置设计，从根上解决。

**可观察的完成标准**
1. 改密码一旦提交，在那之前用旧密码换来的任何访问令牌、pending 令牌、刷新令牌全部无效，**不论**它是在提交之前还是之后签发的
2. 上面的「全部无效」对与改密码并发的登录、二次验证、刷新同样成立
3. 2FA 注册与确认、重新生成恢复码这三种会写入认证材料的操作，不能用改密码之前的会话完成，即使请求在改密码提交之前就已经通过了鉴权
4. 不改密码的用户行为完全不变；部署时已经发出的令牌在用户第一次改密码之前照常可用

**明确不做什么**
- 主动登出某个用户的全部会话、管理员强制下线：可以复用同一个版本号，另开任务
- 停用账号：现在已经靠 `require_current_user` 每次读库判 `ACTIVE` 立即生效，不改
- 修改密码（已登录状态下改密码）的接口：现在没有，以后加入时照本设计 +1
- 访问令牌的有效期和刷新策略：不改

**现有行为与问题证据**
- `app/services/password_reset.py`：重置成功只把该用户的 `refresh_tokens` 置为已吊销
- `app/core/tokens.py`：访问令牌的 claims 是 `sub`、`role`、`sid`、`typ`、`iat`、`exp`、`jti`；pending 令牌类似；都没有和密码状态关联的字段
- `app/api/auth.py` 的 `require_current_user`：只校验签名、类型、过期，以及用户存在且 `ACTIVE`
- `app/services/auth.py` 的 `authenticate`：`session.get(User, …)` 不加锁读用户，`verify_password` 用这次读到的哈希

## 2. 设计概要

### 核心规则：密码版本号

- `users.password_version INT NOT NULL DEFAULT 0`
- **每次由本人设置新密码时**，在已经 `SELECT users … FOR UPDATE` 锁住用户行的事务里 `password_version = password_version + 1`：
  - 现在只有 `reset_password` 一处
  - 客户门户认证（#368）的接受邀请是第二处
  - `create-admin` 命令行建出的新用户版本号是 0，不需要改
- **签发**：签发任何令牌时，把「验证密码时读到的那一行」上的 `password_version` 写进令牌
  - 访问令牌和 pending 令牌：新增 claim `pwv`（整数）
  - 刷新令牌：`refresh_tokens.password_version INT NOT NULL DEFAULT 0`
- **使用**：使用任何令牌时，比较令牌上的版本与库里当前的 `users.password_version`，不相等 → 视为无效
- **兼容**：没有 `pwv` claim 的旧令牌按 0 处理，所以部署前已发出的令牌在该用户第一次改密码之前照常可用；已有的刷新令牌行回填 0

### 为什么这能覆盖并发

令牌上的版本号来自签发者验证密码时读到的同一行。因此：
- 用旧密码通过校验的签发者读到的一定是旧版本号，不管它在改密码提交之前还是之后才提交
- 改密码提交之后，库里的版本号已经 +1，这些令牌在任何使用点都对不上
- 不需要让登录与改密码串行，也不比较时间，没有「同一秒」的边界

### 令牌盘点（签发点、使用点、改密码点）

**改密码点**

| 位置 | 版本号处理 |
| --- | --- |
| `app/services/password_reset.py` 的 `reset_password` | 已经锁用户行；在写新哈希的同一事务里 +1。现有的「吊销全部刷新令牌」保留（多一道） |
| 客户门户认证的接受邀请（#368） | 在锁用户行、写哈希的同一事务里 +1 |
| `app/cli.py` 的 `create-admin` | 新用户，版本号 0，不改 |

**签发点**

| 位置 | 版本号从哪来 |
| --- | --- |
| `authenticate` 签发 pending 令牌（`TOTP_REQUIRED` / `ENROL_2FA`） | 本次 `session.get(User)` 读到的行，即 `verify_password` 用的那一行 |
| `authenticate` 直接签发会话（未启用 2FA 的 CUSTOMER）→ `_complete_login` → `_issue_session` | 同上 |
| `complete_second_factor` → `_complete_login` → `_issue_session` | 消费的 pending 令牌上的 `pwv`（使用点已经核对它等于当前值） |
| `refresh_session` → `_issue_session` | 消费的刷新令牌行上的 `password_version`（使用点已经核对它等于当前值） |

`_issue_session` 新增参数 `password_version`，由调用方传入，**不在函数里重新读用户**：重新读到的可能是改密码之后的新值，会给旧密码换来的会话盖上新版本号。

**使用点**

| 位置 | 令牌 | 检查方式 |
| --- | --- | --- |
| `require_current_user`（所有已登录接口都经过它） | 访问令牌 | 读库时比较 `pwv` 与 `users.password_version`，不等 → 401 `INVALID_TOKEN` |
| `complete_second_factor`（`/login/totp`） | pending | 在事务开头 `SELECT users … FOR UPDATE` 锁用户行（现在是不加锁的 `session.get`），比较，不等 → 401 `INVALID_CREDENTIALS`（与现有「用户不存在或停用」同一个对外结果），不验证第二因子、不发会话。锁一直持有到验证第二因子（写 TOTP 计数器或消耗恢复码）与签发会话之后提交 |
| `/2fa/enrol`、`/2fa/confirm` → `start_enrolment`、`confirm_enrolment` | pending | API 层把 `pwv` 传给服务；服务在写 2FA 行的事务里先 `SELECT users … FOR UPDATE`，比较，不等 → 401 `INVALID_TOKEN`，不写任何 2FA 行 |
| `/2fa/recovery-codes` → `regenerate_recovery_codes` | 访问令牌 | API 层（`app/api/two_factor.py` 的 `regenerate`，现在只传 `user_id`）把访问令牌的 `pwv` 传给服务；服务在替换恢复码的事务里先锁用户行再比较，不等 → 401 `INVALID_TOKEN`，不替换 |
| `refresh_session`（`/refresh`） | 刷新令牌行 | 比较行上的 `password_version` 与当前值，不等 → 与现有过期同样处理（401 `TOKEN_REUSED`，不写重放审计，因为这不是重放）。条件更新失败时的判别见下一节 |
| `logout` | 刷新令牌行 | 不检查：登出只做吊销，对任何令牌都应该成功 |

### 统一加锁顺序（v5）

所有认证路径都按 **用户行 → 认证令牌表**（`refresh_tokens`、`password_reset_tokens`、`two_factor_settings`、`recovery_codes`）的顺序加锁；涉及租户的（客户门户，#368）在用户行之前先锁租户行。插入带 `user_id` 外键的行时，MySQL 会对用户行加共享锁做外键检查，这也算「锁用户行」，所以凡是会插入令牌行的事务，都必须在碰任何令牌行之前先 `SELECT users … FOR UPDATE`。

| 路径 | 加锁顺序 | 现状 | 本设计 |
| --- | --- | --- | --- |
| `reset_password` | 用户 → 重置令牌 → 刷新令牌（批量吊销） | 已是此顺序 | 不变 |
| `refresh_session` | 现在：旧刷新令牌（条件 UPDATE）→ 用户（插入新行时的外键检查） | **与重置相反，会死锁** | 改为：不加锁读出旧行取 `user_id` → `SELECT users … FOR UPDATE` → 条件 UPDATE 旧行 → 比较版本 → 插入新行 |
| `complete_second_factor` | 用户（v3 起开头加锁）→ 2FA 设置 / 恢复码 → 插入刷新令牌 | v3 已改 | 不变 |
| `authenticate` 成功签发 | 用户（更新 `last_login_at`）→ 插入刷新令牌 | 先 UPDATE 用户行再插入，已是此顺序 | 不变 |
| `start_enrolment` / `confirm_enrolment` / `regenerate_recovery_codes` | 用户 → 2FA 设置 / 恢复码 | 本设计加用户锁 | 按此顺序 |
| `logout` | 只锁刷新令牌行 | 不碰用户行 | 不变；它与上面任何一条都不成环 |
| `_register_failure`（失败计数，独立事务） | 只锁用户行 | 调用前外层事务已提交 | 不变 |

**万一仍报死锁**（MySQL 1213，例如将来新代码没遵守顺序）：整个事务回滚，刷新令牌没有被标记已用、也没有新行，对外 500 带 `request_id`，不写重放审计；客户端可以用同一个刷新令牌重试一次（前端现有的 single-flight 刷新失败后会回到登录页，最坏结果是重新登录）。这是兜底，不是预期路径：§7 用屏障验证按上述顺序不会出现死锁。

### 刷新令牌不可用时的判别（入口检查与条件更新失败，同一套规则）

现在 `refresh_session` 有两处会把「已吊销」当成重放（`_treat_as_replay`：吊销整条链、写 `TOKEN_REUSED` 审计、记 `Refresh token reuse detected` warning，T0.9 的盗用告警挂在这条 warning 上）：

- **入口检查**：不加锁读出令牌行后，只要 `used_at` 或 `revoked_at` 非空就进 `_treat_as_replay`
- **条件更新失败**：条件 UPDATE（`used_at IS NULL AND revoked_at IS NULL`）受影响行数为 0 时同样进 `_treat_as_replay`

可是「已吊销、从未用过」只说明它被改密码、登出或整链吊销作废了，不是被盗。于是正常改密码之后，另一台设备的下一次刷新就会触发盗用告警；登出之后同一个令牌再来刷新也一样（既有误报）。改为两处共用一个判别函数：

| 令牌行的状态 | 判定 | 对外结果 | 副作用 |
| --- | --- | --- | --- |
| `used_at` 非空 | 重放或并发抢占 | 401 `TOKEN_REUSED` | 照现有 `_treat_as_replay`：吊销整条链、写 `TOKEN_REUSED` 审计、记 warning |
| `used_at` 为空、`revoked_at` 非空 | 已被吊销（改密码、登出、整链吊销） | 401 `TOKEN_REUSED` | 回滚；**不**写审计、**不**记 warning、**不**再吊销整条链 |
| 都为空、但已过绝对期限或闲置期限 | 过期 | 401 `TOKEN_REUSED` | 照现状，无副作用 |
| 都为空、未过期 | 可用 | 继续刷新 | — |

- 入口检查：不加锁读出的行按上表判定
- 条件更新失败：`SELECT … FOR UPDATE` 加锁重读这一行（`populate_existing`，读最新已提交版本），再按上表判定；若重读后仍是「都为空」（理论上不会出现：条件更新失败却读到可用的行），按重放处理，宁可多踢一次也不放行
- 版本号不符（§2 使用点表）：在锁用户行之后比较，按「已被吊销」那一行处理

### 在途请求的语义（与停用一致）

- 改密码提交**之后**才开始的请求：在 `require_current_user` 就被拒
- 改密码提交**之前**已经通过 `require_current_user` 的在途普通业务请求：可以完成，与现在「停用」的语义相同
- **例外**：写入或消耗认证材料的四种操作，效果会延续到改密码之后，并能把主人锁在门外，所以在自己的写事务里锁用户行、再复查版本：登录第二步（写 TOTP 计数器或消耗恢复码）、2FA 注册、2FA 确认、重新生成恢复码。`reset_password` 锁的是同一行，所以两者排队：
  - 改密码先提交：复查读到新版本，401，不写
  - 写入先提交：写入成立。这是改密码之前、会话仍然有效时完成的操作，改密码随后生效，旧会话从此失效

**完整盘点（会写库的认证路径，v3 逐一核对）**

| 路径 | 写什么 | 是否需要锁内复查 | 理由 |
| --- | --- | --- | --- |
| `authenticate` | 失败计数、锁定（独立事务）；成功时 `last_login_at`、刷新令牌行 | 否 | 不消耗认证材料；签出的令牌带读到的版本号，使用时被拒 |
| `complete_second_factor` | TOTP 计数器或恢复码、`last_login_at`、刷新令牌行 | **是** | 消耗一次性认证材料 |
| `start_enrolment` / `confirm_enrolment` | 2FA 设置、恢复码 | **是** | 写入认证材料 |
| `regenerate_recovery_codes` | 恢复码 | **是** | 写入认证材料 |
| `refresh_session` | 标记旧行已用、插入新行 | 否（另有「刷新令牌不可用时的判别」） | 新行带旧版本号，使用时被拒 |
| `logout` | 吊销整条链 | 否 | 只吊销，对任何令牌都应成功 |
| `request_reset`（忘记密码） | 重置令牌、outbox | 否 | 不依赖会话 |
| `reset_password` | 哈希、版本号 +1、吊销刷新令牌 | —（它就是改密码点） | — |

**锁与失败计数**：`complete_second_factor` 验证第二因子失败时，现有代码先 `session.commit()`（释放用户行锁）再在独立事务里 `_register_failure` 写失败计数。加锁之后这个顺序必须保留：先提交释放锁，再写失败计数，否则独立事务会等待本事务持有的同一行锁。

### 数据库（迁移，编号见 §11）

- `users` 加 `password_version INT NOT NULL DEFAULT 0`，`CHECK (password_version >= 0)`
- `refresh_tokens` 加 `password_version INT NOT NULL DEFAULT 0`，`CHECK (password_version >= 0)`
- 已有行取默认值 0，不加索引：比较都发生在按主键读到的行上

### 令牌格式

- `issue_access_token`、`issue_pending_2fa_token` 新增参数 `password_version`，写入 claim `pwv`
- `decode_token` 不强制要求 `pwv`（兼容旧令牌），由使用点按「缺省为 0」取值
- 不改签名算法、有效期、`typ` 与其余 claim

### 事务边界

- 改密码：版本号 +1 与写新哈希、吊销刷新令牌在同一事务
- 签发：版本号随令牌行（刷新令牌）或随 JWT 一起产生，不另外写库
- 写入认证材料的三种操作：锁用户行、复查版本、写入，同一事务

### 时间与金额

不涉及：比较的是整数版本号，不比较时间。无金额。

## 4. 状态与并发

**版本号**只有一种跃迁：本人设置新密码时 +1。只增不减，没有回退。

**串行化**
- 改密码锁用户行（现状）
- 写入认证材料的三种操作锁同一行后复查
- 登录、二次验证、刷新**不需要**与改密码串行：它们签出的令牌带着读到的版本号，使用点会拒绝过期的版本（§2「为什么这能覆盖并发」）

**数据库保证**：`password_version >= 0`。「只增不减」由唯一写入处（改密码那一条 UPDATE 用 `password_version + 1`）保证。

**幂等**：不新增幂等键。同一张重置令牌只能用一次（现状），所以一次重置只加一。

**重试**：不新增重试。

## 5. 失败与恢复矩阵

| 失败点 | 对外结果 | 数据最终状态 | 是否可重试 | 恢复来源 | 告警 |
| --- | --- | --- | --- | --- | --- |
| 改密码事务提交失败 | 500 | 整体回滚：哈希、版本号、刷新令牌都没变，旧会话照旧有效 | 用同一链接重试 | 用户 | 现有 5xx 日志 |
| 令牌版本不符 | 401（各使用点的错误码见 §2） | 不写任何东西 | 重新登录即可 | 用户 | 无（这是预期行为） |
| 写入认证材料时版本不符 | 401 | 不写 2FA 行、不换恢复码 | 重新登录后再做 | 用户 | 无 |
| 刷新事务遇到数据库死锁（兜底） | 500 带 `request_id` | 整体回滚：旧刷新令牌未用、无新行、无重放审计 | 是，同一刷新令牌重试 | 客户端 | 现有 5xx 日志 |
| 部署窗口（新代码读到没有 `pwv` 的旧令牌） | 照常放行 | 按版本 0 处理 | — | — | 无 |
| Redis/Celery 丢失、外部服务超时 | 不适用：本设计不经队列和外部服务 | — | — | — | — |

## 6. 数据与安全边界

- **租户过滤**：不改。只让更多令牌失效，不放宽任何检查
- **鉴权主体**：不改。版本检查是现有检查之上的一道
- **客户侧字段**：不新增返回字段。`pwv` 在 JWT 里，客户端能解码看到一个整数，它不泄露密码、也不暴露次数以外的信息；可以接受
- **日志、审计、异常**：
  - 不记录令牌原文
  - 版本不符不写审计：它和过期令牌同类，量可能很大，写审计会淹没真正的事件
  - 刷新路径的版本不符**不**按重放处理（不吊销整条链、不写 `TOKEN_REUSED` 审计）：它不是重放，那条链已被改密码吊销
  - 改密码本身已有 `PASSWORD_RESET` 审计，不改
- **密钥**：不新增密钥，不改签名密钥
- **prompt / response**：不处理
- **保留与删除**：新增的两列随用户行、刷新令牌行保留与删除

## 8. 迁移与上线

- **数据迁移步骤**：一个迁移，给两张表各加一列和一条 CHECK，已有行取默认值 0
- **锁表与性能**：两张表都很小（生产 `users` 2 行，`refresh_tokens` 是会话量级）。MySQL 8 加带默认值的列可以即时完成，加 CHECK 会扫表，毫秒到秒级
- **兼容窗口**：
  - 迁移先于代码生效。旧代码写刷新令牌行时，新列取默认值 0；旧代码签发的 JWT 没有 `pwv`，按 0 处理
  - 所以「新迁移 + 旧代码」与「新代码 + 旧令牌」两个窗口里行为都不变
- **部署顺序**：P1 → P3 → P2（§11）
  - P3 上线后、P2 上线前：改过密码的用户版本号已经大于 0，但还没有任何使用点做比较，行为与现状一致
  - P2 上线的那一刻：这些用户在 P3、P2 之间签发的令牌没有 `pwv`（按 0 处理），与库里的版本号不等，被拒一次，重新登录后恢复。没改过密码的用户版本号仍是 0，不受影响
- **回滚或前滚**：生产只前滚。代码回滚到旧版本时，新列被忽略，退回现状（改密码不吊销会话），不会锁死任何人
- **部分部署时的行为**：
  - 只有 +1、没有使用点检查（P3 之后、P2 之前）：等同现状
  - 两者都在才生效；P2 上线时的一次性重新登录见上
- **监控**：不新增告警维度。版本不符按 401 计入现有访问日志

## 9. 方案取舍

| 方案 | 优点 | 风险 | 未采用原因 |
| --- | --- | --- | --- |
| 采用：密码版本号写进令牌，使用时比较 | 不依赖登录与改密码串行；不比较时间；每个使用点只多一次整数比较（`require_current_user` 本来就读用户行） | 漏掉某个使用点就留一个缝 | — 控制：§2 盘点表逐个列出签发点与使用点，§7 对每个使用点都有用例 |
| 备选 A：比较 `iat` 与「改密时刻」（#368 v5 的做法） | 不改令牌格式 | 登录在重置提交前用旧密码通过校验、提交后才签发时，`iat` 晚于改密时刻，被放行（Codex 审查 #368 v5 指出）；秒级精度还有同一秒的边界 | 无法覆盖并发 |
| 备选 B：登录时锁用户行，与改密码串行 | 签发点天然有序 | 每次登录都对用户行加写锁，失败登录的计数提交本来就在独立事务里，再加一层锁让锁顺序变复杂；还要同样处理刷新和二次验证 | 版本号方案不需要任何新锁就能得到同样的保证 |
| 备选 C：服务端记录全部访问令牌（会话表），改密码时逐个吊销 | 可以精确吊销 | 每个请求都要多一次查表，等于放弃 JWT 自包含的好处 | 代价远大于收益；版本号已经足够表达「改密码之前的全部会话」 |
| 备选 D：缩短访问令牌有效期 | 不改代码 | 只是缩小窗口，不关闭它；pending 令牌与在途登录仍然漏 | 不解决问题 |

## 10. 未决问题与假设

- **未决问题**：无
- **假设**：
  - **A1**：`reset_password` 是现在唯一由本人设置新密码的入口（全仓搜索 `password_hash =` 的写入处核对：`cli.py` 建用户、`password_reset.py` 重置）。以后新增的改密码入口必须照本设计 +1，`docs/api.md` 写明
  - **A2**：在途普通业务请求在改密码提交之后完成，与停用的现有语义一致，可以接受
- **需要谁拍板**：无（拆分方式 Kelvin 2026-10-19 已定）
- **如果假设错误**：A1 错了，就有一个入口改了密码却不 +1，旧会话照旧有效。实现时用一个守卫用例扫描 `app/` 下所有给 `User.password_hash` 赋值的地方，要求每一处都同时出现 `password_version` 的递增
