## 1. 目标与边界

- **要解决的问题**：审计行的 `created_at` 在两类写入路径上取整方式不同，导致同一进程里**先发生**的审计可能比**后发生**的审计时间更晚，按时间段筛选在整秒边界上也会差一秒。
- **现有行为与问题证据**：
  - 所有经应用写的审计行都走两条路：`app/services/auth.py` 的 `record_audit(..., now=...)`，以及 `app/repositories/wallet.py` 里直接构造 `AuditLog` 的两处（计费状态跃迁、调账），后者用的是账本行的 `created_at`。
  - `record_audit` 原样写 `created_at=now`。调用方里有 15 个模块先把时刻截到整秒（`utc_now().replace(microsecond=0)` 或同义写法）再传入；另有 5 个模块传的是带微秒的 `utc_now()`：`app/services/auth.py`（登录成功与失败、锁定、登出、2FA 登录、改密码等）、`app/services/password_reset.py`、`app/services/two_factor.py`、`app/cli.py`（建管理员）、`app/ai_api/ops.py`（outbox 运维动作）。
  - 列是 MySQL `DATETIME`（无小数秒，迁移 0002）。仓库没有设置 `sql_mode`，未启用 `TIME_TRUNCATE_FRACTIONAL`，所以 MySQL 对带小数秒的值**四舍五入**到整秒；截好的值原样存。两种取整混用：`02:49:15.6` 写的登录审计存为 `02:49:16`，之后 `02:49:15.9` 写的建客户审计存为 `02:49:15`。生产上实际出现过这种倒序（TODO 历史记录 AIH-TASK-006 记录段，`docs/archive/TODO_RECORDS_2026-09-30.md`）。
  - 测试里 SQLite 保留微秒，看不到这个差异；只有生产的 MySQL 会出现。
  - 已有的规避：管理端审计查询按自增 `id` 倒序（`app/services/audit_query.py` 模块说明、`docs/api.md`「排序」），并在返回时 `.replace(microsecond=0)`。
- **可观察的完成标准**：
  1. 经 `record_audit` 写的每一行，`created_at` 等于传入时刻**向下截到整秒**的值，SQLite 与 MySQL 结果相同（MySQL 上传入 `…:16.6` 存为 `…:16`，不是 `…:17`）。
  2. 因而全部审计写入路径用同一个单调不减的取整函数：同一进程里时刻 `a ≤ b` 的两次写入，存下的 `created_at` 也满足 `≤`。
  3. `docs/api.md`「排序」与 `audit_query.py` 模块说明里「取整不一致」的说法改成现在的真实原因（见下一条），删掉「按时间段筛选在整秒边界上可能差一秒」。
- **明确不做什么**：
  - 不改 `utc_now()` 本身：它还被锁定截止、会话、TOTP 步长、令牌过期等非审计逻辑使用，改它会扩大到认证语义本身。
  - 不改认证路径写的**其他列**（`users.last_login_at`、会话与令牌表、锁定时刻等）：它们在 MySQL 上仍是四舍五入，与本问题（审计行之间的顺序）无关；如需统一另开一项。
  - 不改历史审计行：`audit_logs` 由迁移 0010 的触发器保证只追加，spec §66 也禁止修改；历史行保持原样（最多比真实时刻晚 1 秒）。
  - 不改排序依据：仍按自增 `id`。原因不再是取整，而是**时刻在插入之前取**：并发的两个请求，先取时刻的那个可能后插入，`created_at` 与 `id` 的顺序本来就可能不一致。
  - 不设置 `sql_mode`：那会改变全库所有带小数秒写入的行为，影响面远超本任务。

## 2. 设计概要

```text
调用方（任意时刻 now，可能带微秒）
  → record_audit(session, ..., now=now)
  → AuditLog(created_at = now.replace(microsecond=0))   ← 唯一改动
  → session.add（事务由调用方提交，与业务写入同一事务，不变）
```

- **输入、输出与错误契约**：`record_audit` 的签名不变；`now` 仍是必填的 naive UTC。行为变化只有一处：写入的 `created_at` 是 `now` 向下截到整秒。不新增错误。
- **为什么在 `record_audit` 里截，而不是改 5 个调用方**：截在唯一的写入点，以后新增的调用方不可能再漏；5 个调用方里的 `moment` 同时用于锁定、会话、令牌等非审计列（§1 不做），只截审计这一处才不扩大影响面。截到整秒的函数对已经是整秒的值是恒等的，原来截好的 15 个模块行为不变。
- **钱包里直接构造的两处**（`app/repositories/wallet.py` 的计费状态跃迁审计与调账审计）用账本行的 `created_at`。写账本的只有 `post_transaction`，它的两个调用方 `app/services/usage_billing.py`、`app/services/wallet_adjustments.py` 都先截到整秒，所以这两处已经是整秒，本任务不改它们。
- **新增或修改的 API**：无。管理端审计查询的响应格式不变（`created_at` 本来就按整秒返回）。
- **数据库**：无迁移，无新列、新索引。
- **事务边界**：不变。审计仍与对应的业务写入同一事务（INV-13）；登录失败、锁定等独立事务写审计的路径照旧。
- **时间语义**：审计 `created_at` 的含义从「调用方取的时刻，MySQL 上可能被四舍五入」统一为「调用方取的时刻向下截到整秒」。取整只发生在写入时，读取侧的 `.replace(microsecond=0)` 保留（对整秒是恒等，且让契约不随存储后端变）。
- **金额**：不涉及。

## 8. 迁移与上线

- **数据迁移**：无。不回写历史行（§1）。
- **锁表与性能**：无；每次写审计多一次内存里的 `replace`。
- **兼容窗口 / 部分部署**：单进程内的纯写入时取值变化；新旧版本并存的几十秒内，旧版本写的登录审计仍可能被四舍五入，与现状相同，无新风险。
- **部署顺序**：合并即部署，无前置步骤。
- **回滚**：回退提交即可；已写入的整秒值在旧代码下同样合法。
- **监控**：无新增；不影响告警。

## 9. 方案取舍

| 方案 | 优点 | 风险 | 未采用原因 |
| --- | --- | --- | --- |
| 采用：在 `record_audit` 里向下截到整秒 | 唯一写入点，一行改动；新调用方不会再漏；与 15 个已截模块的取整方向一致（都是向下） | 认证路径其他列仍是四舍五入（§1 不做） | — |
| 备选 A：改 5 个调用方，把各自的 `moment` 截到整秒 | 同一事务内审计与其他列时间一致 | 这些 `moment` 还用于锁定截止、会话、令牌过期、TOTP 步长；截掉会改变认证语义（例如锁定提前最多 1 秒结束），要逐个论证；以后新增调用方还可能漏 | 影响面大于问题本身 |
| 备选 B：`utc_now()` 直接返回整秒 | 一处改动覆盖全部 | 同备选 A，且波及所有用 `utc_now()` 的非审计逻辑 | 同上 |
| 备选 C：数据库连接设 `sql_mode` 含 `TIME_TRUNCATE_FRACTIONAL` | 应用代码零改动 | 改变全库所有 `DATETIME` 写入；SQLite 测试仍保留微秒，测试与生产继续不一致 | 影响面过大，且不解决测试与生产的差异 |
| 备选 D：在 `record_audit` 里四舍五入（与 MySQL 一致） | 认证路径的审计值与现在相同 | 已截的 15 个模块是向下截；改成四舍五入要么改它们，要么继续混用 | 向下截是现有多数路径的约定，改动最少 |
