# 数据治理：PDPA 与数据留存

> spec §136 要求维护的文档之一。依据：spec §13（只存元数据）、§94（日志）、§98.1（备份与恢复）、§112（数据留存）、
> §112.1（关户）、`REQ-PRIV-001`、上线闸门 Gate 2「PDPA and data-retention policy approved」（[REQUIREMENTS.md](REQUIREMENTS.md)）。
> 决策记录：[ADR-0017](adr/ADR-0017-data-retention.md)（**提议中**）。
> **状态：草稿。**本文所有保留期数字都是**建议值**，逐条列在 §10「待 Kelvin 拍板」，批准前一律不算已定；
> 引用的马来西亚法律条文与时限由法律 / 会计顾问核对（spec §112 要求政策「基于马来西亚法律、会计、合同与 PDPA 意见」）。
> 最后更新：2026-11-19

## 0. 一页结论

- **财务记录与个人数据分开定保留期**（spec §112）。财务记录建议「至少 7 年」，V1 **不实现**财务记录的到期清理（最早到期在
  2034 年初，见 §6.3）；个人数据在用途结束后删除或不可逆匿名化。
- **清理只做「到期且已终结」的行**，用定时任务分批删除，每次运行写一条审计汇总；**绝不**绕过触发器、**绝不**用
  `TRUNCATE` / `DROP`（§6）。
- **能清的**：认证令牌、outbox 终态行、AI 模块 outbox 终态行、通知、核对运行记录、关户客户的联系人与门户账号（§4）。
- **清不了的**（被不变量或触发器挡着）：账本、用量事件、冲突记录、收据、定稿对账单、审计日志、汇率拉取记录、各类价格版本（§11）。
  其中审计日志的 IP / UA、用量事件的 `conversation_id`、收据与对账单快照里的公司名**含或可能含个人数据而无法匿名化**，需要 Kelvin 决定接受还是改设计。
- **年备份现为永久保存**，与 PDPA「不超过目的所需」冲突，建议改为 7 年（§5、§10 K16）。
- 数据主体的访问 / 更正请求：Kelvin 决定、管理员执行，法定 21 天内答复（待核），§8。数据泄露：发现 → 控制 → 评估 → 72 小时内报专员（待核）→ 通知受影响者，§9。

## 1. 范围与原则

**范围**：本仓库（Central Billing 与同进程的 AI 模块，ADR-0012）的 MySQL 库、它的日志、离机备份与配置快照；Billing Client
（`integration-client/`）在接入方本地的 SQLite outbox 只列出保留规则，由接入方执行。各接入方（Integrated Application Backend）自己的数据不在本文。

**原则**：

1. **只存元数据**（spec §13、Invariant 9）：不存 prompt、AI 回复、完整对话。本文的数据类别以此为前提。
2. **财务与个人数据不共用一条规则**（spec §112）：财务保留期不是无限期保留联系人数据的理由。
3. **三种到期动作**：`保留`（法定或业务上仍需要）、`删除`（整行删除，库里不留痕迹）、`匿名化`（行保留供外键与财务追溯，个人数据列改成固定的不可识别值，不可逆）。
4. **不可变的仍不可变**：Invariant 4、5、6、11、12 与审计只追加，由 MySQL 触发器保证。清理不得删除、修改这些行，也不得为清理临时删触发器。
   财务记录到期后的清理另写 ADR、另过设计闸门（§6.3）。
5. **关户不删数据**（AIH-TASK-209 设计 §6「数据与安全边界」）：关户只是把租户置为终态；个人数据的处理按本文 §7 的时间线另行进行。
6. **个人数据不进日志、不进异常消息、不进审计的前后状态**（`REQ-PRIV-001`；`app/services/customers.py` 文件头）。现有代码已按白名单写审计，本文不改变这一点。

## 5. 库外数据：日志、备份、导出、第三方

### 5.1 日志（spec §94；deployment.md §7）

| 对象 | 现状 | 保留期 |
| --- | --- | --- |
| 容器日志（json-file） | 按大小轮转（`max-size 10m` / `max-file 3`） | 按大小，不是保留期 |
| 本机日志归档 | `deploy/log_ship.sh` 每日打包加密，`BILLING_LOG_RETENTION_DAYS` 默认 30 天，`shred -u` 删除 | K14（30 天，决策 ⑤ 暂定） |
| R2 `logs/` | lifecycle 35 天 | K14（35 天） |

访问日志带客户端地址，所以日志是个人数据，30 / 35 天的上限同时满足 §94 的事故调查与 PDPA 的最小保留。

### 5.2 备份（spec §98.1；deployment.md §5.2.1「R2 上的保留期」，Kelvin 2026-09-14 定）

| 前缀 | 内容 | 现行保留 | 建议 |
| --- | --- | --- | --- |
| `full/` | 每日全量 | 35 天 | K15：维持 |
| `binlog/` | binlog | 35 天 | K15：维持 |
| `monthly/` | 每月首份全量 | 366 天 | K15：维持 |
| `yearly/` | 每年首份全量 | **永久** | **K16：改为 7 年**（与 K1 对齐） |
| `config/` | 部署配置快照（不含个人数据） | 366 天 | K17：维持 |

**备份与匿名化的关系**：匿名化与删除只作用于线上库，已存在的备份里仍有原值，直到该备份按保留期过期。所以：

- 线上库匿名化之后，个人数据最长还在备份里留「该备份的保留期」那么久；年备份永久就是永久，这是 K16 要改的原因。
- **从备份恢复后必须重新执行清理**：§6 的清理都是**按规则**（「过期满 N 天」「关户满 N 个月」），恢复后的下一轮定时任务会自动重做，
  不依赖被恢复掉的审计记录。**按请求**做的提前匿名化（§8）规则重做不了，要另记一份登记表（只记租户 `public_id` 与日期，不记个人数据），
  放在库外的工单系统里，恢复演练与真实恢复后逐条重做。这一步写进 runbook「整台 VPS 没了」的恢复后对账。
- 备份上传前已加密，主密钥不进 R2（deployment.md 决策 ⑦），备份本身泄露不等于明文泄露。

### 5.3 导出与文档

客户 CSV 导出同步生成、不落盘（AIH-TASK-113 设计 §1）；Excel 导出与 CSV 同一套数据，生成时 openpyxl 在临时目录写一个临时文件，保存成功时随即删除，出错时由 `write_xlsx` 按固定步骤删除，ZIP 只在内存里拼（`app/core/xlsx_export.py`，设计闸门 #753）。出错路径上删除本身也失败时，异常被吞掉，文件会留在 api 容器的 `/tmp`；`/tmp` 挂的是内存文件系统（`docker-compose.yml` 的 `tmpfs`，128 MB），不落宿主机磁盘、不进备份，容器重启或重新部署即清空，需要立即清除时重启 api 容器；收据与对账单 PDF 从快照即时生成、不存文件。spec §112「导出文件的留存与安全删除」在服务器侧只涉及上面这种 Excel 临时文件。
客户下载到本地的文件由客户自己保管。

### 5.4 第三方

- **Stripe**：付款人填写的邮箱、姓名与卡信息只在 Stripe。本库按会话 id 去 Stripe 查，不复制。关户与删除请求涉及 Stripe 侧数据时，按 Stripe 自己的数据删除流程处理（是否需要、能否删除由顾问确认，Stripe 自身也有法定保留义务）。
- **邮件服务**：投递日志由服务方按其条款保留。
- **Cloudflare R2**：只存加密后的备份与日志归档。
- **Healthchecks**：只有计数与状态，没有个人数据。
- 以上服务的数据可能存放在马来西亚境外，跨境传输是否需要额外措施列在 §10 K22。

### 5.5 Billing Client（接入方本地）

`integration-client/` 的 SQLite outbox：已送达行保留 `delivered_retention_seconds`（缺省 7 天、至少 1 天，须不短于中心的灾备重放窗口；
设计闸门 #571），死信、`ops_log` 与 `incidents` 不自动删；文件随接入方的备份策略。spec §21 要求 `SENT` 保留期不短于中心灾备重放窗口，
中心的重放窗口目前没有成文的数字，见 §10 K18。

## 6. 清理机制原则

详细决策见 ADR-0017。所有清理任务都遵守：

1. **定时任务**：Celery Beat 每天一次，排在每日全量（马来西亚 03:17）与日志外送（03:47）之后的低峰时段。Redis / Celery 丢了只是这一轮不跑，下一轮照常（Invariant 14）。
2. **只删到期且已终结的行**：条件里同时写「终态」与「早于截止时刻」，删除语句按主键执行并**在 `DELETE` 的 `WHERE` 里重复这两个条件**，挡住选出之后被改回非终态的行。
   `PENDING`、`PROCESSING`、`SENDING`、`HELD`、`RETRY`、未复核等非终态一律不碰。
3. **批量上限**：每批按主键升序最多 1000 行、一个短事务；每轮每张表有总上限（建议 50 000 行），超出留到下一轮；不加钱包、租户行锁，不与计费抢锁。
4. **审计一条汇总**：每轮运行写一条审计（新动作，例如 `DATA_RETENTION_PURGE`，操作者为系统），`after_state` 只有每张表的截止时刻与删除行数，不含任何行内容。
   删除行数为 0 的表不写。
5. **不绕过数据库保证**：用运行账号执行，不 `TRUNCATE`、不 `DROP`、不删触发器、不关外键检查。外键或触发器拒绝即视为缺陷：本轮停止、记错误日志、告警，不重试别的写法。
6. **开关与只读演练**：每个清理项有独立配置开关，缺省关；有「只数不删」模式，上线前先在生产只数一轮核对数字。
7. **按规则、可重放**：清理条件只依赖行本身的状态与时间，恢复备份后自动重做（§5.2）。

### 6.1 匿名化的原则

- 匿名化是**不可逆**的：个人数据列改成固定的占位值（非空列用不可投递、不可识别的唯一占位值，可空列置空），不用可还原的哈希或加密。
- 与被匿名化的行同一事务写一条审计，前后状态只有租户 / 用户的对外 id 与「已匿名化的字段名」，不含原值。
- 匿名化之后，管理端仍能按 `public_id` 查到租户与它的财务记录，只是联系人信息不可见。

### 6.2 财务记录到期之后

财务记录（K1）、审计（K3）的到期清理**不在 V1**：最早一批（2026 年的记录）按 7 年、自所属日历年末起算，要到 2034 年 1 月才到期。
届时要另写 ADR 解决 §11 第 1–6 条的冲突（期初结转、事件 id 墓碑、触发器改为按期限放行），并过设计闸门。在那之前，这些表的行全部保留。

关户流程本身见 [runbook.md「关户」](runbook.md#关户) 与设计 [AIH-TASK-209-account-closure.md](design/AIH-TASK-209-account-closure.md)。

## 8. 数据主体的访问与更正请求

spec §112.1：V1 可以不做自助的隐私请求界面，但上线前必须有运营流程。以下就是这个流程。

### 8.1 渠道与身份核实

- 渠道：客户合同与隐私声明里写明的联系渠道（隐私声明本身是上线前要准备的文件，不在本仓库）。请求一律书面（邮件或信件）。
- 身份核实**不能只看发件地址**：发件人可以伪造，回复地址也可以指向别处。至少做到下面一项，核实方式记进工单：
  - 管理员**新建**一封邮件（不点「回复」，不用请求里给的回复地址）发到库里登记的联系邮箱或门户账号邮箱，附工单号与一次性核实码，请求人从该地址回复核实码；
  - 按合同里登记的电话回拨核实；
  - 客户授权签字人书面确认，签字人的身份同样按合同登记的联系方式回拨核实。
- 核实不了的不提供任何数据，只回复「无法核实身份」，也不确认或否认账号是否存在。
- **答复只发往已核实的登记地址**：新建邮件发到库里登记的联系邮箱或门户账号邮箱，不发往请求里另给的地址；含个人数据的附件加密，密码经另一渠道（例如登记的电话）告知。
- 只提供请求人本人的数据，或其有权代表的那个租户的数据（Invariant 8）。
- 每个请求开一个工单；**工单号**是之后所有原因字段里唯一可写的东西。

### 8.2 谁做、多久回复

| 步骤 | 谁 | 时限（待核，§10 K19） |
| --- | --- | --- |
| 确认收到 | 管理员 | 3 个工作日内 |
| 判断范围、拒绝或部分拒绝的理由 | Kelvin | — |
| 执行并答复 | 管理员 | 收到后 **21 天内**（PDPA 访问请求与更正请求的法定时限，条文由顾问核对）；需要延期的，按法定程序在期限内书面通知 |

### 8.3 访问请求

本平台持有的某个人的个人数据，按 §3 的清单逐项查：

- 租户联系人：`tenants` 的联系人三列（管理端客户详情）。
- 门户账号：登录邮箱、状态、最近登录时刻、是否启用 2FA（不提供哈希与密钥）。
- 与该账号有关的审计：动作、时刻、IP 与 UA（管理端审计查询，按用户筛选）。
- 收据与对账单：快照里的公司名在个体户或以个人名义签约时就是人名（§3），属于个人数据，在范围内。门户账号还在时客户可在门户自行下载；
  门户账号已按 §7 删除后，由管理员在管理端下载该租户的收据与对账单 PDF（收据与对账单的管理端下载接口，`app/api/admin_payments.py`、`app/api/admin_statements.py`），按 §8.1 的方式交付。
- 账本与用量事件不含联系人数据（`conversation_id` 不应含，§3），不在访问请求的范围内；客户为对账需要用量明细时另按工单处理。

答复里不得包含其他租户或其他人的数据（Invariant 8）。

### 8.4 更正请求

| 数据 | 怎么改 |
| --- | --- |
| 租户联系人、公司名 | 管理端编辑客户资料（`CUSTOMER_UPDATE`，审计只记字段名）。`CLOSED` 之后仍允许 |
| 门户登录邮箱 | 门户账号重发邀请时改邮箱（`PORTAL_INVITATION_RESENT`，审计记 `email_changed`） |
| 已开具的收据、已定稿的对账单里的公司名 | **不能改**：不可变财务快照（spec §106、Invariant 12、收据触发器）。答复里说明理由；之后开具的单据使用更正后的公司名 |
| 审计、账本里的内容 | 不能改（只追加）。若是我方误写了个人数据，按 §11 记录并告知 |

### 8.5 删除请求或撤回同意

- 可做：提前匿名化联系人、删除门户账号（与 §7 同一操作，提前执行）。在 R4 任务上线前由管理员手工按 runbook 做；之后由管理端入口做。
- 不可做：法定保留期内的财务记录与审计。答复里写明保留依据与预计到期时间。
- 提前做的匿名化要记进 §5.2 的库外登记表，备份恢复后重做。

## 9. 数据泄露通知要点

### 9.1 什么算泄露

个人数据被未授权访问、披露、修改或丢失，例如：数据库或备份连同主密钥一起外泄、管理员账号被盗用、日志或导出被发到错误的人、
某个租户看到了另一个租户的数据（Invariant 8）。

### 9.2 步骤

1. **发现与上报**：任何人发现疑似泄露，立即报 Kelvin；管理员同时开事故工单，记下发现时刻。
2. **控制**：按 runbook 已有的条目止损——吊销被盗凭据或会话（改密码使全部会话失效）、轮换集成凭据与 webhook 签名密钥、主密钥事故按「主密钥丢失或要在新主机上重建」一节；
   保全现场（日志归档、审计）后再修。
3. **评估**（发现后 24 小时内完成初评）：涉及哪些数据类别（§3）、多少人、是否加密（备份与凭据密文有主密钥保护，密码与令牌只有哈希）、是否可能造成重大损害。
4. **通知专员**：PDPA 修订后的泄露通知义务——发现后 **72 小时内**通知个人数据保护专员（时限与格式以专员指引为准，由顾问核对，§10 K20）。
5. **通知数据主体**：可能造成重大损害时，在通知专员后的法定期限内（指引为 7 天，待核）通知受影响的个人；B2B 合同另有约定的，同时通知受影响的租户。
6. **记录**：泄露登记表记下时间线、范围、措施与通知记录（不在登记表里复制泄露的个人数据），按法定期限保留。
7. **复盘**：根因、补救、要改的设计，结论写进 REVIEW-LOG 或新 ADR。

### 9.3 本平台降低泄露影响的既有措施

只存元数据（Invariant 9）；密码 Argon2id、令牌与恢复码只存哈希；集成凭据、webhook 密钥、TOTP 密钥信封加密（ADR-0004），主密钥不进备份桶；
备份与日志归档加密后离机；日志不记邮箱、令牌、密钥（§94）；网关事件不存原始请求体。

## 11. 与不变量冲突或无法清理的表

逐条核对迁移里的触发器与外键、以及读这些表的代码之后的结论：

1. **`wallet_transactions`**：BEFORE DELETE 无条件拒绝（0006，Invariant 5）。另外，每日钱包核对（`ledger_problems`）要求序号从 1 连续、首行 `balance_before`
   从 0 链起；删掉旧行即使绕过触发器，核对也会报 `SEQUENCE_GAP` 等问题。到期清理需要「期初结转」机制 + 改触发器的迁移。
2. **`usage_events`**：没有 DELETE 触发器，但 `event_id` 全局唯一是 Invariant 2、11 的唯一防线，而摄取对 `occurred_at` **没有过去的下限**
   （`app/services/usage_ingest.py`：晚到事件合法）。删掉旧事件后，同一 `event_id` 再次上报（接入方 `replay_delivered`、补录、重放攻击）会被当作新事件再扣一次费。
   清理前需要墓碑表或摄取的时间下限。另外 `PROCESSED` 行的任何 UPDATE 都被拒绝（0018），所以 `conversation_id` 里若有个人数据**无法匿名化**。
3. **`usage_event_conflicts`**：BEFORE UPDATE / DELETE 无条件拒绝（0017），且以 RESTRICT 外键指向 `usage_events`：有冲突记录的事件永远删不掉。
4. **`audit_logs`**：BEFORE UPDATE / DELETE 无条件拒绝（0010）。`ip_address`、`user_agent` 是个人数据，只能随整行在 K3 到期时处理；`reason` 里误写的个人数据无法清除。
5. **`payment_receipts`**：BEFORE UPDATE / DELETE 无条件拒绝（0039）；快照里的公司名不可改。它以 RESTRICT 引用 `payments`，所以**开过收据的支付也删不掉**。
6. **`monthly_statements`**：`FINALIZED` / `VOID` 的 UPDATE / DELETE 被拒绝（0035，Invariant 12）；快照里的公司名不可改。
7. **`fx_fetch_attempts`**：BEFORE UPDATE / DELETE 无条件拒绝（0015）。无个人数据、每天约 3 行，接受永久保留。
8. **价格、规则、汇率、税务版本**：DELETE 触发器 + 被快照外键 RESTRICT 引用，永久保留（K2）。
9. **`domain_outbox` 的三类无处理器事件**：设计上永久 `PENDING`，「只删终态」的规则永远清不到它们（K10）。没有个人数据，只是体量。
10. **年备份**：现行永久保存，已匿名化或删除的个人数据会永久留在离机备份里（K16）。
11. **`tenants`、`users`（ADMIN）**：被十余张表 RESTRICT 引用，行删不掉，只能匿名化。`tenants.email`、`users.email` 非空（后者唯一），占位值必须满足约束。
12. **残余风险**（各迁移文件头已写）：`TRUNCATE` / `DROP` 是 DDL，不经触发器。清理任务只用运行账号，「迁移账号与运行账号拆分」（TODO 待登记）完成前，这一点只靠约定。
