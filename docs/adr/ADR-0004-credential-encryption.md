## 背景

spec v1.0 的 §36 与 §37 自相矛盾：§36 说「secret 只存安全哈希」，§37 又要求 HMAC 请求签名。**HMAC 验签需要服务端持有密钥材料，只存哈希根本验不了签。** 这是 [SPEC_REVIEW_v1.0.md](../SPEC_REVIEW_v1.0.md) 的 P0-2，评审判定「这条不改，实现方一定会做错」。

v1.1 已修正，§36 现在明确要求**认证式可逆加密**，并写死「口令式单向哈希对这些密钥无效」。原则定了，但没定用什么实现——本 ADR 补这一层。

## 已定的原则（来自 spec，不在本 ADR 的决策范围）

| 项 | 要求 | 出处 |
| --- | --- | --- |
| API Key | 非机密标识符，可按查找形式存储 | §36 |
| 签名 Secret | 认证式可逆加密存储 | §36、§74.4 |
| 主密钥位置 | **存在数据库之外**，通过生产密钥管理注入 | §36 |
| 主密钥备份 | 独立访问控制，单独备份，纳入恢复流程 | §36、§98.1 |
| 泄露面 | 日志、审计前后值、API 响应、异常栈**都不得**出现明文 | §36、§94 |
| 轮换 | 支持有界重叠期 + 显式 `key_version`；过期后旧版本停止验签 | §36 |
| 展示 | 创建后**永不**再次返回明文 | §36、§74.4 |
| 撤销 | 每个 API key 可独立撤销 | §36 |

`integration_credentials` 已有 `encrypted_secret` 与 `key_version`（§74.4），`projects` 有 `encrypted_webhook_secret` 与 `webhook_key_version`（§76）。

⚠️ 早期草稿在此写「表结构不因本 ADR 而变」——**这句不成立**：入站凭据的轮换重叠期现有结构支持，但出站 webhook 密钥的重叠期需要一处暂存，现有单槽结构放不下。详见第 4a 节。

## 决策

### 1. 加密机制：应用层信封加密（选项 A）

```text
明文 secret
  → AES-256-GCM 加密（数据密钥 DEK）
  → DEK 用主密钥加密后，与密文同存
主密钥（KEK）→ 宿主机文件，经 Docker secret 注入
```

不引入外部 KMS。理由见「备选方案 B」。

### 2. 主密钥注入：Docker Compose `secrets:`（file 源），**不用环境变量**

主密钥以只读文件挂进容器（`/run/secrets/<name>`），进程启动时读一次载入内存。

**为什么不用环境变量** —— 环境变量从四个地方漏：

- `docker inspect <container>` 直接看得到
- `/proc/<pid>/environ`，任何能进容器的进程都能读
- 崩溃转储；不少 APM / 日志库会整个抓取环境变量
- 子进程自动继承

⚠️ **权限必须按容器运行用户来设，不能想当然写 `root:root 0400`**（Codex 审查发现，2026-09-10）：

Docker Compose 的 `file:` 型 secret 走 **bind mount**，`uid` / `gid` / `mode` 三个选项**只在 swarm 模式生效，普通 compose 下被忽略**。宿主机文件的属主与权限会原样带进容器。所以：

```text
宿主机文件 root:root 0400  +  容器以非 root 运行  =  进程读不到，服务起不来
```

正确做法：

- Phase 0 先确定 API / Celery 容器的**运行 UID**（非 root）
- 宿主机主密钥文件**属主设为该 UID**，权限 `0400`
- **不要为了读密钥把容器改回 root 运行**——那是用一个更大的问题解决一个小问题

其余要求：

- compose 文件里**只写路径不写值**
- 不进仓库、不进镜像
- ⚠️ **路径与文件名本身也不写进本仓库**（仓库是公开的，见 [ADR-0001](ADR-0001-repository-visibility.md)），只写在私有附录里（边界见第 6 节）

### 3. 备份：与数据库备份**分开存放，两套访问控制**

> **主密钥若与加密后的数据库躺在同一个备份里，加密等于没做。** 一次泄露两样全丢。

- 数据库备份 → §98.1 的加密异地存储
- 主密钥 → 另一处、另一套凭据，外加一份离线副本
- **两者的访问权限不得由同一个凭据打开**

### 4. 轮换 —— 两种「版本」必须分开，不能混

⚠️ 本项目里有**两个互不相干的版本概念**，早期草稿把它们混成了一个，这里明确拆开：

| 概念 | 字段 | 客户端可见？ | 变的是什么 |
| --- | --- | --- | --- |
| **签名密钥版本** | `key_version` / `webhook_key_version`（§36、§37、§74.4） | **可见**，随 `X-Acuven-Key-Version` 请求头传 | HMAC 密钥**明文本身**换了 |
| **加密封装版本** | 加密层内部元数据，不在上表字段里 | **不可见** | 只是密文的包裹方式换了，明文没变 |

#### 4a. 签名密钥轮换 —— **入站与出站不是一回事**

⚠️ 早期草稿用一套流程覆盖两者，但**谁在验签**不同，重叠期落在谁身上也不同（Codex 审查发现，2026-09-10）。

##### 入站：集成凭据（`integration_credentials`，平台验签）

平台是验签方，所以重叠期由**平台**承担：同时接受旧、新两个 `key_version`。

```text
1. 新增一行凭据，分配新 key_version，与旧行并存
2. 【重叠期开始】平台同时接受两个版本的签名
3. 应用后端切换到新密钥（改配置，重启）
4. 监控旧行的 last_used_at，确认不再有旧签名到达
5. 【重叠期结束】旧行置 revoked，此后一律拒绝（§36）
```

✅ **现有表结构支持**：§74.4 的 `integration_credentials` 是**一凭据一行**，且已有 `key_version` / `status` / `valid_from` / `valid_until` / `last_used_at` / `revoked_at`，多行并存天然可行。

##### 出站：Webhook 签名密钥（`projects`，平台签名、应用后端验签）

平台是**签名方**，任一时刻只用一把密钥；验签的是应用后端，**重叠期落在后端那边**。

```text
1. 生成新 webhook secret，先送达应用后端
2. 【重叠期开始】应用后端同时接受旧、新两个 webhook_key_version
3. 平台切换到新密钥签名（原子切换，不需要并存）
4. 确认新签名被接受后，通知后端停止接受旧版本
```

⚠️ **现有表结构不完全支持**：§76 的 `projects` 只有**一组** `encrypted_webhook_secret` + `webhook_key_version`，没有 `last_used_at`、没有 revoked 状态、**也没有暂存「下一把密钥」的位置**。第 1 步（先送达再切换）在当前 schema 上无处安放。

因此**本 ADR 修正一处早先的说法**：并非「表结构完全不变」。Phase 1 实现凭据管理时必须二选一：

- **方案 i（推荐）**：新建 `project_webhook_secrets` 表，结构对齐 `integration_credentials`（多行、带版本与状态）。与入站语义统一，将来支持多下游也不用再改
- **方案 ii**：`projects` 加一组暂存列（`next_encrypted_webhook_secret` / `next_webhook_key_version`）。改动小，但只能暂存一把，且语义与入站不一致

选定后更新本节，并在 Phase 1 的设计闸门里体现。

##### 两者共同的约束

- 重叠期长度必须配置化并写进 runbook，**不得硬编码**
- 重叠期结束前必须确认旧版本已无流量，否则会出现全量验签失败
- §37 已明确签名时间戳是**本次发送时刻**、每次重试重新生成，所以 outbox 积压不需要额外延长重叠期

#### 4b. 加密封装轮换（换 DEK 或换主密钥）

**只重新加密密文，明文密钥不变，`key_version` 不变，客户端完全无感。**

- 换 DEK：重新加密该条 secret
- 换主密钥：**只重新包裹 DEK，不碰 secret 密文本身**

第二条正是选信封加密、而不是「直接用主密钥加密所有 secret」的原因：直接加密的话，主密钥轮换要把全表解密再加密一遍。

> **绝不要因为重新加密而递增 `key_version`。** 那会让客户端以为签名密钥换了，触发一次没有必要的、且没有对应新明文密钥的轮换。

### 5. 重放保护存储：Redis，**过期时刻 = 请求 timestamp + 5 分钟**

⚠️ 早期草稿写的「TTL = 6 分钟」**是错的**，会留下约 4 分钟的重放窗口。推导：

```text
签名时间窗是 ±5 分钟，所以带「未来 5 分钟」时间戳的请求也会被接受。

T+0    请求首次到达，其 timestamp = T+5（未来 5 分钟，合法）
       → 记下 nonce，若 TTL = 6 分钟，则 T+6 过期
T+6    nonce 已过期
       → 但该请求的时间戳有效期是 timestamp ± 5 分钟 = 到 T+10 才失效
T+6 ~ T+10   两道防线同时失效，重放通过  ← 洞
```

**正确做法：nonce 的过期时刻按请求自己的 timestamp 算，而不是「记录时刻 + 固定 TTL」。**

```text
nonce 过期时刻 = 请求 timestamp + 时间窗（5 分钟）
```

这样精确覆盖该请求的整个有效期，不多不少。

若实现上必须用固定 TTL，则 **TTL ≥ 2 × 时间窗 = 10 分钟**（取 11 分钟留余量），因为最坏情况下一个请求从首次出现到彻底失效跨度是两个窗口。

#### 存储按端点分两类（2026-09-10 定，采纳部分审查意见）

§37 要求「不得把 Redis 硬编码为唯一重放存储，持久化选择必须扛得住要求的故障模型」。分析结果是**分两类处理**，不是一刀切：

| 端点 | 改钱？ | 已有的**永久**防护 | nonce 存储 |
| --- | --- | --- | --- |
| `POST /integration/usage-events` | 是 | `usage_events.event_id` UNIQUE（永久，无 TTL） | Redis |
| `POST /integration/usage-events/batch` | 是 | 同上，逐条生效 | Redis |
| `GET /integration/account-status` | 否 | 只读，重放无害 | Redis |
| `GET /integration/health` | 否 | 只读，重放无害 | Redis |
| **`POST` 支付 Webhook（§91）** | 是 | `(gateway, gateway_event_id)` UNIQUE | **数据库（持久）** |

**为什么支付 Webhook 落库**：它是**唯一真正来自外部**的入站端点——由支付网关打进来，不是 Acuven 自己的机器。量小（每笔充值一次），写库的代价可以忽略，换来重启不丢的重放防护。

**为什么其余四个用 Redis 就够**：

- 前两个已经有**永久、无 TTL 的持久化重放防护**——`event_id` 唯一约束。Redis 丢了，重复的用量事件照样被数据库挡住，至多产生一次财务效果（Invariant 11）
- 后两个不改任何状态，重放本身无害
- §37 原文要求的是把重放保护**与**领域幂等**结合**（combine），不是要求两层各自独立达标

**这是一次显式的风险接受**：Redis 重启或被清空后，上述四个端点在一个时间窗内失去 nonce 层保护。财务上无缺口，但认证层的纵深确实短暂降级。若将来这四个端点中出现**没有领域幂等键**的写操作，本决定必须重新评估。

> 审查方（Codex）主张五个端点全部落库。分歧点在于「领域幂等能否折抵认证层要求」。决策人裁定采用上面的分类方案，理由与代价如上。记录见 [REVIEW-LOG.md](../REVIEW-LOG.md)。

## 使用场景（实现时对着这节看）

### 主密钥在哪些时刻被用到

**先澄清一件容易混的事：主密钥只保护「密钥材料」，不保护业务数据。** 钱包余额、账本、用量事件在库里都是明文——spec 没要求加密它们。

需要加密存储的只有两样：

| 存在哪 | 是什么 | 谁用 |
| --- | --- | --- |
| `integration_credentials.encrypted_secret` | 应用后端**签请求**用的 HMAC 密钥 | `ai_chatbot_demo` 上报用量时签名 |
| `projects.encrypted_webhook_secret` | 平台**签 webhook**用的密钥 | 平台推送停机 / 复机状态时签名 |

**场景 A —— 每次验签（最热的路径）**

```text
应用后端调完 AI 供应商
  → outbox worker POST 用量事件，带 HMAC 签名
  → 计费平台收到，要验签
  → 需要该 project 的密钥【明文】
  → 取出密文 → 解密 DEK → 解密 secret
```

这是**每一条用量事件都要走一次**的路径。因此实现上：容器启动时读一次主密钥载入内存，解密结果短期缓存，**不是每个请求去读一次文件**。

**场景 B —— 每次发状态 webhook**

钱包扣成负数 → 状态转 `SUSPENDED` → 平台推签名 webhook → 需要出站签名密钥明文 → 解密。

**场景 C —— 创建 / 轮换凭据**

管理员为新 project 建凭据 → 生成 secret → 加密入库 → 只在创建那一刻返回一次明文，之后永不再返回（§36）。

> ⚠️ §98.1 要求的「加密的异地备份」用的是**另一把钥匙**，管的是备份文件本身。和主密钥是两回事，**不得共用同一把**——否则备份泄露等于两样一起丢。

### 重放保护在哪个时刻起作用

**位置**：平台的 API 入口，对每个带签名的请求检查「这个 `X-Acuven-Request-Id` 见过没有」。

**为什么光有签名不够**：重放是把同一份字节原样再发一次——字节没变，**签名当然还是有效的**。签名证明「这是谁发的、没被篡改」，证明不了「这是个新请求」。

时间线：

```text
10:00:00  worker 发请求  Request-Id=req_abc  Timestamp=10:00:00
10:00:01  平台：签名有效 → 查 Redis 无 req_abc
          → 记下 req_abc，过期时刻 = Timestamp + 5 分钟 = 10:05:00
          → 正常处理

10:00:30  同一份字节被原样重发
10:00:31  平台：签名【仍然有效】——字节没变，签名当然还对
          → 查 Redis → req_abc 已存在 → 拒绝

10:07:00  同一份字节又被重发
10:07:01  平台：Timestamp 10:00:00 已超出 ±5 分钟窗口
          → 直接拒绝，连 Redis 都不用查
```

**nonce 的过期时刻必须跟着请求自己的 timestamp 走**，两道防线才严丝合缝：nonce 一过期，时间戳检查正好接上。

⚠️ 用「记录时刻 + 固定 TTL」会错，因为时间窗是 **±**5 分钟——带未来时间戳的请求，其有效期会超出 nonce 的存活期。详见上面第 5 节的推导。

**谁会重放**（按现实程度排）：

1. **最常见的不是攻击，是 bug** —— outbox 重试逻辑写错，同一份请求发了 10 次
2. 内部日志或反向代理记下了完整请求体，后来被翻出来重发
3. Acuven 自己某台机器被拿下
4. 网络中间人抓包 —— 生产是 HTTPS，这条基本被 TLS 挡住

**为什么 Redis 够用**：两端都是 Acuven 自己的机器、走 HTTPS（§2.1），威胁本就低；而且真被重放，**财务上也没事**——

- 重放用量事件 → `event_id` 全局唯一约束挡住，至多一次财务效果（Invariant 11）
- 重放支付回调 → `(gateway, gateway_event_id)` 唯一挡住，不会重复入账（§74.7）

所以 §37 才要求「财务性请求必须把重放保护**和**领域幂等结合」：**幂等是安全网，重放保护是纵深防御的第二层。** Redis 丢失只让第二层临时失效，不会捅出财务窟窿。

> 失效时长的准确说法是**最长约 10 分钟**，不是 5 分钟：时间窗是 ±5 分钟，一个带未来时间戳的请求从首次出现到彻底失效跨两个窗口（推导见第 5 节）。早期草稿写「5 分钟」是同一处 ± 疏忽的连带错误。

> 唯一真正来自外部的入口是支付 Webhook（§91，由网关打进来）。**该入口的 nonce 落数据库**（见第 5 节），且**选定网关时需额外确认其回调是否自带幂等标识**——并入 [TODO.md](../TODO.md) 的 D6 选型评估。

## 6. runbook 的公私边界

spec §136 要求**仓库内**的 `docs/runbook.md` 覆盖 `encryption master-key recovery`；[ADR-0001](ADR-0001-repository-visibility.md) 又规定敏感细节不得进公开仓库。早期草稿只写了「不进本仓库」，没定义两者怎么共存（Codex 审查发现，2026-09-10）。边界定义如下：

| 放哪 | 写什么 | 举例 |
| --- | --- | --- |
| **`docs/runbook.md`**（本仓库，公开） | **流程**：步骤顺序、判断点、前置条件、验证方法、找谁 | 「确认主密钥备份可读 → 恢复到临时位置 → 验证能解密一条已知凭据 → 重启 API → 抽查一条验签」 |
| **私有附录**（仓库外，受控） | **具体值**：主机路径、文件名、备份存储位置、访问凭据、联系人 | 实际路径、实际桶名、谁持有访问权 |

规则：

- `docs/runbook.md` 用**占位符**指代具体值，并注明「实际值见私有附录 §master-key」
- 私有附录的**存放位置本身**也不写进仓库
- 判断标准：**一个拿到公开仓库的人，应该能看懂流程，但拿不到任何一个能用于访问的具体值**

这样 spec §136 的「仓库内覆盖」与 ADR-0001 的公开约束同时满足。

## 备选方案

### B. 外部 KMS（云厂商）

- ✅ 主密钥永不离开 KMS，审计与轮换托管
- ❌ **与 §99 的单 VPS 无云依赖冲突**，引入外网调用与账单
- ❌ KMS 不可达时验签全挂 —— 会成为验签路径上的新可用性依赖
- ❌ 为一个尚无客户的 V1 引入云绑定，不划算

**未采用。**

### C. SOPS / age 之类的文件级加密

- ✅ 适合加密**配置文件**
- ❌ 不适合**运行时逐条解密数据库里的 secret**，每次验签都要调外部进程
- ❌ 轮换粒度太粗

**未采用。**

## 后果

### 正面

- 无外部依赖，`REQ-AVAIL-001` 不新增故障点
- 与 §98.1 的备份 / 恢复方案能统一设计
- 主密钥轮换只需重新包裹 DEK，不必全表重加密

### 负面 —— 已知代价

- **主密钥的保管完全是自建流程**，没有托管服务兜底。流程写不清楚就是最大的单点风险
- **主密钥丢失 = 所有 secret 不可恢复。** 不是「数据丢了」，而是所有集成凭据与 webhook 签名密钥全部作废，**每个 Integrated Application Backend 都要重新配置**
- 因此 §98.1 的季度恢复演练**必须真的演练主密钥恢复**，否则备份等于从未验证过；§136 的 runbook 已列「encryption master-key recovery」
- 密钥管理相关的主机路径、文件名等细节不得写进本仓库，运维文档要分两处存放，维护成本上升
