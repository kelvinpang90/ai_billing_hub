## 背景

spec §47 已经定了骨架：V1 三个通道（Portal / Email / WhatsApp）、**复用 Acuven 既有的 Email 与 WhatsApp 服务**、**必须实现 Notification Adapter 抽象**、**不得重建 WhatsApp 基础设施**。

决策人 2026-09-11 给出具体指向：Email 参考 `rs-roof-pms`，WhatsApp 复用既有网关。两条都与 §47 一致。

但「参考」与「照搬」之间有一条必须划清的线，而「复用网关」这条在核实后发现前提不成立。本 ADR 处理这两件事。

## 决策

### 1. 一切通知走 Notification Adapter 抽象（spec §47 强制）

业务代码只依赖 Adapter 接口，不直接调 SMTP 或任何 WhatsApp API。

这一条不是可选的工程品味：§47 写着 "Central Billing must implement Notification Adapter abstraction"。而被参考的 `rs-roof-pms` **恰恰没有这一层**——它是模块级函数直调，测试只能 monkeypatch 模块属性。照搬它的结构会直接违反 §47。

### 2. Email 传输层借 `rs-roof-pms`，**投递模型不借**

**借这些**（都是踩过坑的代码，值得原样拿）：

| 借什么 | 为什么 |
| --- | --- |
| `aiosmtplib` + 标准库 `EmailMessage` 的 SMTP 直连 | 不绑供应商。换服务商只改配置不改代码 |
| 465 / 587 的 TLS 分支判定 | 两个 TLS 参数互斥，传错不是报错而是**静默挂起到超时**。这是别人已经踩过的坑 |
| 「空 host = 未配置」是合法状态 | 开发与 CI 不需要真实邮箱凭据就能跑通全流程 |
| 发送函数不抛异常、返回布尔 | 邮件服务器抖动不该把业务端点打成 500（呼应 Invariant 1） |
| 发件人地址与认证用户名分离配置 | 用 relay + API key 认证时两者不是一回事 |

**不借这些**（`rs-roof-pms` 的做法与本项目的不变量直接冲突）：

| 不借什么 | 冲突在哪 |
| --- | --- |
| 请求内同步发送 | 它在 HTTP 请求路径上等 SMTP 往返。本项目的通知由后台流程触发，且 Invariant 1 要求计费侧故障不得拖累主链路 |
| 零重试、无发送记录 | **违反 Invariant 14**：一次 SMTP 失败 = 这封信永久消失，只剩一行日志，无法补发、无法审计。对密码重置尚可（用户会自己重试），对「对账单就绪」不可接受 |
| 无模板层（正文是硬编码字符串拼接） | 本项目有收据、对账单、低余额、停机 / 复机等多类通知，且面向马来西亚客户需中英双语。字符串拼接在第二类通知出现时就会失控 |
| 调用方无法区分是否发出 | 那是密码重置专用的**反用户枚举**要求。本项目恰恰必须知道有没有发出去 |

### 3. 投递模型：domain Outbox + 异步 worker + 周期性恢复

照 spec §25、§74.6 与 §98.1：

1. 业务事务内**同时**写入通知 Outbox 记录（Invariant 13：原子提交）
2. 提交后由 worker 投递
3. **周期性恢复任务**从数据库 Outbox 状态重建丢失的投递任务（Invariant 14：Redis / Celery 丢了也能恢复）
4. 重试带退避，次数与下次重试时间持久化在 Outbox 行上（`attempt_count`、`next_retry_at`）

**同一个逻辑通知重试多次不得产生第二条逻辑通知**（spec §48）。去重键落在 Outbox 行，不是落在发送时刻。

### 4. 通知只在**状态跃迁**时发出，不在每次余额变动时发

spec 第 371 行：低余额、停机、复机通知只在实际状态跃迁时发出。阈值触发需要 rearm 语义——余额回到阈值以上之后，下一次跌破才再次触发。

这条写进本 ADR 是因为它决定 `notifications` 表要存阈值状态，而不只是存「发过什么」。

### 5. WhatsApp：不自建基础设施，但传输路径本 ADR 不选定

方向遵循 §47：**不重建 WhatsApp 基础设施**，WhatsApp 作为 Notification Adapter 的一个实现接入。

具体走哪条传输路径**待定**，理由见下节。在选定之前：

- Adapter 接口按「支持模板化消息 + 需要投递状态回执」设计，不要按「发一段纯文本就完事」设计
- Phase 6 的 WhatsApp 部分不得开工
- **Email 与 Portal 两个通道不被阻塞**——三通道是独立 Adapter 实现

## ⚠️ WhatsApp：为什么还不能落地

核实既有网关（`whatsapp_gateway`）后发现，「复用」在当前状态下不成立。这不是配置问题，是能力缺口：

1. **网关已停机**（2026-08-31 停容器），零流量；出站端点虽然存在，但**自部署以来调用次数为 0**，未经任何真实验证
2. **Meta 的 24 小时客服窗口是硬规则**：顾客主动来信后 24 小时内才可自由发文本，超出只能发**已审批的模板消息**。本项目的三类通知（低余额、支付成功、对账单就绪）**全部是我方发起、与顾客上次来信无关**，绝大多数落在窗口外
3. **网关没有模板消息能力**，只会发纯文本；也不记录 last-inbound 时间，判断不了窗口。结果是 Graph API 报错、网关把错误码吞掉只返回一个笼统的 5xx，调用方连失败原因都拿不到
4. **顾客的回信会被路由到别的下游**：出站路径不写会话归属，顾客回复时按号码分流会落到聊天机器人 demo，计费平台收不到
5. **出站侧无幂等、无重试、无发送记录、无投递状态回执**；且所有下游项目**共用一枚对称密钥**，网关无法区分一条消息是哪个项目发的——既无法审计也无法按项目限流
6. **凭据链路本身是断的**：网关的 App 与 system user 所属的 Meta portfolio，其 WhatsApp 能力已被永久停用；真实客服号的 WABA 在另一个 portfolio，两者互不可见且 system user 不能跨 portfolio 迁移

第 5 条对本项目尤其致命：**通知重复发给客户是真实投诉**，而出站侧连幂等键都没有。

## 备选方案

### A. Email 用 API 服务（SendGrid / SES / Postmark 等）替代 SMTP —— 未选，但保留

优点是投递事件回调、退信自动抑制、模板托管、发送分析都现成，而 SMTP 直连这些全都没有。

否定理由：§47 要求复用 Acuven 既有 Email 服务，现有资产就是 SMTP；且引入新供应商要走选型与合同。**但这是可逆的**——只要第 1 节的 Adapter 抽象到位，换成 API 服务只改一个 Adapter 实现。这正是坚持要 Adapter 抽象的实际收益之一。

**已知缺口记在这里**：SMTP 直连**没有退信（bounce）与投诉处理**。硬退信会持续投递，长期损害发送域名声誉。Phase 6 之前需要一个抑制列表方案，本 ADR 不定。

### B. 照搬 `rs-roof-pms` 的同步发送模型 —— 未选

否定理由见第 2 节：违反 Invariant 14，且失败后无法补发、无法审计。

### C. 计费平台直连 Meta Graph API，绕开既有网关 —— 未选定，但**不排除**

网关存在的理由是**分流**：一个 Meta App 只能配一个 webhook URL，多个项目共用一个号码时需要有人分发入站消息。

如果计费通知使用**独立 App / 独立号码**，就不存在分流需求，也就不需要这个网关——而 §47「不得重建 WhatsApp 基础设施」的本意是不要重复造轮子，不是强制绑定某一个具体服务。

这条与「复活并扩建网关」哪个成本更低，需要实测后判断，本 ADR 不下结论。

## 后果

### 正面

- Email 与 Portal 两个通道不被 WhatsApp 的问题阻塞，Phase 6 可以先做这两个
- Adapter 抽象让 Email 传输层的选择可逆（SMTP → API 服务只换一个实现）
- Outbox 投递模型直接满足 Invariant 13 / 14，且与支付、Webhook 复用同一套恢复机制

### 负面 —— 已知代价

- **比 `rs-roof-pms` 复杂得多。** 那边是 73 行一个模块；这边要 Adapter 接口 + Outbox 表 + worker + 恢复任务 + 模板层 + 去重。复杂度是不变量要求的，不是设计过度——但它确实意味着 Phase 6 的工作量远大于「抄一个 email_service 过来」
- **SMTP 直连拿不到投递事件**，发出去之后是否真的到达无从得知，只能靠客户反馈
- **没有退信抑制**（见备选方案 A），需要在 Phase 6 前补方案
- **WhatsApp 通道的落地时间不可预测**，取决于选哪条路径，且两条路径都涉及 Meta 侧审批（模板审批要排队）

## 收口条件

**Email 与投递模型部分已可进入实现**（Phase 6），无阻塞条件。

**WhatsApp 部分**需先完成：

- [ ] 在「复活并扩建既有网关」与「计费平台独立 App / 号码」之间做出选择，并评估两者成本
- [ ] 无论选哪条，都必须解决：模板消息能力、24 小时窗口判定、会话归属与回信路由、出站幂等、投递状态回执、按项目的凭据与限流
- [ ] Meta 侧：模板提交审批（需排队）；若涉及 marketing 类模板，还需 opt-in 留证机制
- [ ] 凭据链路：确认可用的 Meta portfolio 与 WABA 归属

选定并落地后在本 ADR 原地补完，文件头「修订」一行追加记录。

**在此之前，Phase 6 的 WhatsApp 部分不得开工；Email 与 Portal 不受此限制。**
