## 背景

系统侧 AI API（员工用的只读 AI 能力，第一项是 CRM 客户摘要）原本是独立仓库、独立部署的 `acuven_ai_api`：自己一个库、一个 outbox、一个投递 worker，用 HMAC 把用量上报本平台；它的调用方身份是部署环境里一段手工维护的 JSON（`client_id` → token 摘要、本平台的租户与项目 ID、集成 key / secret、能力列表），要与本平台后台的租户和项目人工对齐。

2026-10-12 只读核实：它已于 2026-10-10 部署到 VPS（只在内网），但 outbox 为空、0 个客户端绑定、从未发生真实调用。

spec 原来的立场是两条：

- §2.1 / ADR-0002：集成方与计费平台是**独立的信任域与故障域**，只走认证 REST 与签名 Webhook，**永不共享数据库**。
- §135：V1 不做 central AI Gateway。

## 决策

决策人 2026-10-12 的八条（MERGE）：

1. `acuven_ai_api` 并入本平台，合成**一个服务进程**：同一个应用、一套部署、一个数据库。理由：AI 调用与 AI 计费在概念上是一体。
2. 计费仍异步、不阻断 AI 调用。
3. Chatbot（`acuven_aichat`）仍是外部接入方，不经 AI 模块调模型。
4. 取消「AI API 按项目部署到客户机器」的例外。
5. 现在就合并，第 3 阶段试点改在合并后的服务上验收。
6. AI 模块自己的用量仍走 HMAC 签名上报（自调）。
7. AI 调用方与计费的「租户 × 项目」统一成一套身份。
8. 接受与计费共用发布节奏，但要有缓解措施。

落到本仓库（spec §141，设计闸门 #281）：

- AI 代码是一个子包；请求路径只读 AI 密钥、模型目录与租户 / 项目状态列，只写自己的 outbox；不 import 钱包、账本、定价、汇率、支付、摄取与计费代码，由 import 白名单测试机械保证。
- 它是 §2.1 唯一的例外：唯一一个既调模型、又在计费信任域内的组件。其余集成方的隔离规则不变。
- **功能定义放在调用方**（决策人 2026-10-13）：AI 模块只负责调用模型与计费，只有一个通用接口 `POST /v1/messages`（供应商 Messages API 的子集 + 必填的功能标签 `feature`）。提示词、输入输出格式、解析、质量评测与防提示注入都在 CRM 等调用方里做，加功能只改调用方。护栏：只许模型目录里 `ACTIVE` 的模型，请求体与 `max_tokens` 有上限。
- **用量带功能标签**（决策人 2026-10-13）：`feature` 随用量事件进摄取端、存进 `usage_events`，后台可按功能筛选；摄取契约里是可选字段，外部接入方可不带；不参与计价。
- 它只服务 Acuven 自己的模块后端，不给 Chatbot 等外部接入方转发模型调用；spec §121 / §135 的「不做中央 AI 网关」收窄为「不给外部接入方做网关」。
- 用量经签名摄取 API 送到本平台自己的端点，与外部接入方同一套验签、幂等与入账；签名侧沿用 `acuven_ai_api` 独立写成的那份实现，不与验签侧共用代码，自调才真的验了契约。
- 状态在进程内直接读权威列（不存本地副本、不收 webhook、不做对账）；模型返回后 outbox 提交报错时先核查是否其实已写入（已写入则照常返回），确认未写入或核查不了才返回 503 不回正文，偏离 spec §20（决策人 2026-10-12 确认，设计 #281 §10）；§20 的最高级告警与可审计人工对账照做。
- `/v1` 对公网开放（决策人 2026-10-12，Q3，取代 2026-10-09 的「AI API 只在内网访问」）：不在这台 VPS 上的模块后端走公网 HTTPS，同机的走内网；公网入口靠 AI 密钥与边缘按来源限速防护。
- `acuven_ai_api` 现在下线（决策人 2026-10-12，Q5）：2026-10-12 已禁用它的部署工作流、删除 VPS 上的两个容器；空库保留 30 天。

## 备选方案

### A. 保持独立服务（现状）

**未采用**（决策人 2026-10-12）。两套身份要人工对齐；两套部署、两个库、两份运维。

### B. 同一个镜像起两个容器，按角色开关路由

AI 容器不随计费的发布重启，健康检查也分开。

**现在不做，作为退路**（决策人 2026-10-12，E-20）。多一个容器、一套编排与健康检查；仍共用同一个库，可用性耦合只少了「进程」那一半。发布耦合真的造成问题时再启用。

### C. AI 用量直接调用摄取函数，不走 HMAC

少一次本机 HTTP。

**未采用**（决策人 MERGE 第 6 条）。AI 模块要 import 摄取代码，边界破了；自调不再走外部接入方那条路，第 3 阶段试点就验不到签名、时间窗、nonce 与回执。

### D. AI 表放在共享基建 `infra_mysql` 的独立库里

本平台的库出故障时 AI 不受影响。

**未采用**（决策人 E-17「一个数据库」）。两套连接、两套备份；身份表与租户 / 项目不在同一个库里，复合外键保证不了归属（INV-8）。

### E. 每个功能一个专用接口，提示词放在 AI 模块（设计 #281 v2）

AI 模块能控制每个功能的输入输出与提示词，密钥只能做被允许的事。

**未采用**（决策人 2026-10-13）。每加一个功能，AI 模块与调用方两边都要改，还要在后台开通；功能本来就是业务逻辑。

## 后果

**正面**

- 身份只有一套：开租户、开项目、签 AI 密钥都在同一个后台，不再人工对齐。
- AI 模块的状态检查读的是权威数据，停用与余额停机即时生效，不受 webhook 延迟与对账周期影响（spec §119 的 5 分钟滞后对它不存在）。
- 自调让第 3 阶段试点在本仓库的 CI 里就能端到端测：AI 调用 → outbox → 签名 → 摄取 → 计费。

**负面（明知的代价）**

- **可用性耦合变大**。原来 `acuven_ai_api` 的库在共享 `infra_mysql` 上，与本平台的专用 MySQL 是两个实例；合并后本平台 MySQL 不可用（磁盘写满、恢复演练、迁移出错）或 api 进程不可用，AI 也不可用。spec §141.5 把 `REQ-AVAIL-001` 对 AI 模块的含义收窄为「计费功能（摄取、定价、钱包、计费 worker、Redis）出错不得拖垮 AI」，这是对 Invariant 1 字面的一次收窄，不是保持。
- **发布耦合**。改钱包、支付、后台页面也会重启 AI。单容器的 `compose up -d` 是先停后起：AI 请求有 75 秒总时限、优雅停机 85 秒，在途调用都能跑完，但这段时间新的 AI 请求拿 502；万一优雅期到点被强制取消，那次调用也会留下最高级告警与待处置记录。缓解：健康检查拆成 `/healthz/ai` 与 `/healthz/billing`、部署冒烟以前者为准、AI 改动与支付 / 钱包改动不进同一个 PR；退路是方案 B。
- **计费进程第一次在内存里处理业务内容**（联系人快照、模型输出）。Invariant 9 只禁存储，但日志、异常、审计都要防；靠哨兵字符串测试守住，审查时要多看一眼。
- **偏离 spec §20**（决策人 2026-10-12 确认）：模型已返回、outbox 提交报错时先用新连接核查：其实已写入就照常返回；确认未写入或核查不了才返回 503 不回正文——这次 token 已花，调用方却什么也没拿到。§20 的另外两项照做：立即记最高级告警（只有元数据），库恢复后把这次用量落成一条 `HELD` 记录，由人工决定计费还是作废；若发现它其实已写入且已进入投递，就标记人工复核并告警，复核结论（保留或调账退回）留审计。停机时被取消的调用同样处理（设计 #281 v5）。进程在落库前重启时，只剩那条告警日志。合并后 outbox 与鉴权在同一个库，这种失败意味着库刚刚不可用，概率低。
- **密钥泄漏的后果变大**（通用接口的代价）：拿到一把 AI 密钥就能用目录里的任何模型做任何事，费用记在那个项目上；内部租户不扣钱、也没有上限（E-14）。控制：吊销即时生效、单次上限、按来源限速、模型只限目录内。
- **防提示注入与输出质量全靠调用方**：AI 模块不加系统提示、不检查内容。它只返回文本、不执行动作，所以注入的后果停在调用方怎么用这段文本。
- **spec §121 / §135 收窄**：原来的「V1 不做中央 AI 网关」现在只对外部接入方成立。
- **计费进程多了一个公网入口**。未鉴权的请求也会到 api 进程、每个 401 都读一次库；靠 256 位随机 token 与边缘按来源限速挡，但 AI 流量与计费接口共用同一个进程的资源。另有两项不在本仓库的前置：`infra_nginx` 对 `/v1` 的读超时（默认 60 秒，要 90 秒）与 Cloudflare 对非浏览器 POST 的质询。
- **自调验不到跨主机网络与时钟偏差**：签名方与验签方同机同钟，±300 秒时间窗、DNS、TLS、Cloudflare 这些只有 `acuven_aichat` 接入时才验得到。
- **多了一个运行时依赖**（async HTTP 客户端），以及一个只挂给 api 的 secret 文件（Anthropic key）；宿主机文件缺失时 compose 起不来，必须在合并前建好。
