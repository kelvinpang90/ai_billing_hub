## 背景

评审 R1 担心两件事：

1. **边界死锁**：欠 RM50、充 RM50，余额正好为 0，租户永远卡在挂起。
2. **抖动**：余额在 0 附近来回，状态、webhook、通知跟着来回。

评审建议用可配置的双阈值 `suspend_at` / `resume_at` 加滞后带（例如 ≤ -RM5 停、≥ RM10 复）。

spec 1.1 之后，**第 1 件已经解决**：§7 第 10 条把 RM0 归到 `SUSPENDED`，§42 要求充值时计算并强制「最小恢复额」，使结果余额严格大于 RM0。**第 2 件大部分解决**：§7 第 11 条与 §48 规定通知只在真实跃迁时发，低余额告警要从阈值上方跌破才触发、回到上方才重新武装。

剩下的事实：

- 停机规则仍是字面量 `balance <= 0`（spec §49；代码在 `app/repositories/wallet.py` 的 `billing_status_for`，`verify_wallet` 用同一规则核对）。`tenants` 表（§75）没有任何停机阈值字段。
- 这与 §42「最低充值额不许写死、要能在管理端配置」的原则不一致。评审跟进（v1.1 第 4 条）的结论是「可接受的取舍，但应显式记为已知决定，而不是留白」—— 这就是本 ADR 要补的。

### 抖动到底还剩多少

只有**贷方**能让租户从 `SUSPENDED` 回到 `ACTIVE`：用量只会扣钱（§8），挂起期间继续扣费不产生跃迁（代码里状态不变就直接返回）。所以「停 → 复 → 停」的每一圈都必须有一笔充值或管理员调账。抖动的频率上限是**充值次数**，不是用量次数 —— 不会出现用量风暴刷状态的情况。

真正剩下的坏情形只有一个：**恢复后余额太小**。最小恢复额若只保证「严格大于 RM0」，客户可能只多充了 RM0.01，复机后下一个请求就再次停机。每一圈都会产生一次 `status_version` +1、一条复机 webhook、一条停机 webhook 与两条通知。

### 透支（坏账）有多大

V1 不做同步预扣（§7 第 6 条），新请求只被应用侧缓存的有效状态拦住，透支被明确接受（§7 第 7 条）。透支窗口 ≈ 用量从发生到扣款的延迟（§119：p95 ≤ 60 秒、p99 ≤ 5 分钟）+ 状态传到应用侧的延迟（webhook p95 ≤ 60 秒，对账兜底 ≤ 5 分钟）。窗口里客户照常消费，这部分金额在停机时已经是负数。停机阈值定在 0 还是定在 +X，决定的是这段透支从哪里开始算。

## 决策

**推荐方案 A**：保持 `balance <= 0`，把它记为已知决定；滞后效果交给 Phase 4 的最小恢复额去做，不在停机规则上做。

具体是三条：

1. 停机 / 复机规则维持 spec §49 与 §7 第 8–10 条原样：余额 ≤ 0 为 `SUSPENDED`，> 0 为 `ACTIVE`，RM0 挂起。代码不改。
2. **Phase 4 的 §42 设计闸门**必须把「最小恢复额」定义成：清掉欠款之后，还要留出一个可配置的余额缓冲（例如「最低充值额」本身），而不是只比 0 多一分钱。这样既不偏离 §42 的字面要求（结果严格大于 RM0），又消掉「充 RM0.01 复机、下一个请求就停」的循环。缓冲取值属于 §42 的管理端设置，不写死。
3. 透支量先观测、不预防：Phase 3 试点时记录每次停机时的余额（负多少），§120 已要求「钱包负余额」告警。若观测到透支金额有实质影响，另写 ADR 评估方案 B，并以试点数据为依据。

## 备选方案

| 方案 | 做法 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 维持 0，缓冲放在最小恢复额里**（推荐） | 停机规则不变；§42 的最小恢复额 = 欠款 + 可配置缓冲 | 与 spec §49、§7 第 8–10 条、§24「充值只改计费状态」完全一致，不需要偏离 spec 的 ADR；代码、测试、`verify_wallet` 都不改；缓冲只在复机那一刻起作用，解决的正是唯一剩下的抖动场景 | 停机阈值仍是字面量 0，与 §42「不写死」的原则仍不对称；透支不做预防 | 推荐 |
| **B. 可配置的单一停机阈值**（例如余额 ≤ +RM5 就停） | `tenants` 或全局设置加 `suspend_at`，复机仍是 > `suspend_at` | 提前停机，能吃掉在途用量，减少透支与坏账 | 偏离 §49（要写偏离 ADR）；客户账上还有钱却被停，§7 第 9 条「余额回到 RM0 以上即自动复机」与 §42「最小恢复额使余额严格大于 RM0」都要跟着改；`verify_wallet` 的一致性规则要带上阈值；阈值变更本身也会让状态跃迁（要定义改阈值时是否重算、是否 +1 版本） | 不推荐现在做；留作透支数据出来后的选项 |
| **C. 双阈值加滞后带**（评审原建议，停 ≤ `suspend_at`、复 ≥ `resume_at`） | `tenants` 加两列，停与复分开判定 | 最彻底地消除 0 附近的抖动；两个阈值都可配置 | 偏离 §49 与 §7 第 9 条；**状态不再是余额的函数**：同一余额（在带内）可以是 ACTIVE 也可以是 SUSPENDED，`verify_wallet` 不能再由余额推出应有状态，得存历史或改成区间校验；带内充值后「钱到账却不复机」要向客户解释，§42 的最小恢复额计算也要改成以 `resume_at` 为目标；复杂度全落在钱的核心路径上 | 不推荐：它解决的问题（抖动）已被「只有贷方能复机」与方案 A 的缓冲覆盖，代价却落在账本一致性上 |

## 后果

**好的**

- 余额决定状态这条规则保持为纯函数：`verify_wallet` 能由余额直接推出应有状态，现有测试（跨零、正好为 0、挂起中扣费）全部继续有效。
- 不偏离 spec，不需要改 §49、§7、§24。
- 唯一剩下的抖动场景由 §42 的设计闸门一次性处理，并且缓冲可配置。

**坏的（必须知道的）**

- 停机阈值仍然写死为 0，与 §42「最低充值额不写死」的原则不对称。这是有意的：停机阈值决定的是余额与状态的对应关系，最低充值额只是一个输入校验，两者的改动代价不同。
- 透支不做预防。V1 已经接受透支（§7 第 7 条），但接受多少没有数字；直到 Phase 3 试点前，都没有实测的透支量。
- 管理员调账也能让租户复机（调账是贷方）。管理员若只贷记一小笔，同样会出现「复机后马上再停」。这是操作问题，不在本 ADR 的规则里防，调账界面（AIH-TASK-017）在确认步骤里显示调账后的余额与计费状态，让管理员看得到。
- 如果以后改走方案 B 或 C，要写新 ADR 取代本 ADR，并迁移已有的状态语义。
