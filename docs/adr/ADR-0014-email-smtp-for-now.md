## 背景

[ADR-0013](ADR-0013-email-api-service.md) 同日较早时定了「Email 改用带退信与投诉回调的 API 服务」，还没有任何实现。决策人随后改为：**现阶段只用 SMTP**。

按 [ADR 修订规则](README.md#修订规则)，改变已生效的决策要写新 ADR，所以由本 ADR 取代 ADR-0013，而不是原地改它。

## 决策

### 1. Email 继续走 SMTP，ADR-0009 第 2 节恢复有效

传输层仍按 ADR-0009 第 2 节借 `rs-roof-pms` 的 SMTP 实现（`aiosmtplib`、465 / 587 的 TLS 分支、空 host = 未配置、发送不抛异常），投递模型照旧走 Outbox + worker + 周期恢复。ADR-0009 的其余各节不受影响。

### 2. 不设期限，出现以下任一情况时重新评估 API 服务

- 客户反馈收不到收据、对账单或余额提醒，且查明是送达问题
- 发件域名被列入黑名单，或邮件成批进垃圾箱
- 退信需要人工处理的频率高到成为日常工作

重新评估时，ADR-0013 第 2 节的准入条件 E1–E5 可以直接拿来用。

### 3. 退信与投诉缺口先接受

- 不做抑制列表，也不接收退信邮件。ADR-0009 里「Phase 6 之前需要一个抑制列表方案」（备选方案 A 末段与「后果」负面一条）由本节取代，不再是 Phase 6 的开工前提；触发第 2 节任一条件时再一并解决
- Outbox 行只记录「SMTP 服务器是否接收了这封信」，记录不了「最终是否送达」
- 退信与投诉只能靠客户反馈发现

### 4. 发件邮箱沿用 `rs-roof-pms` 的那个账号

账号与密码走部署环境配置，不进仓库。上线前要确认三件事：该账号已开通并能发信、发件域名属于 Acuven、该域名的 SPF / DKIM 已配置。`REQ-LAUNCH-001` 要求的真实账号验证照常适用。

## 后果

### 正面

- 不引入新供应商，没有选型、开户和额外费用
- 不需要新增投递事件回调端点，也就少一个设计闸门
- 与 spec §47「复用 Acuven 既有 Email 服务」的字面一致

### 负面 —— 已知代价

- **收据与对账单是否送达无从得知**，只能靠客户反馈
- **硬退信会被反复投递**，长期损害发件域名信誉
- **与 `rs-roof-pms` 共用发件账号**：两边的发送量与信誉互相影响，一边出问题另一边一起受牵连；账号密码轮换要两个项目同时改配置
- 等到触发条件出现再换，是在问题已经影响客户之后才处理
