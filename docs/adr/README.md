# ADR — 架构决策记录

> spec §136 要求：中心摄取语义、财务期间与 cut-off、凭据加密、生产数据库隔离、外部供应商选型
> 这几类决策**必须在对应实现阶段之前**落成 ADR。
> 最后更新：2026-09-10

---

## 什么时候写 ADR

满足任一条就写：

- 决策改变系统的财务、安全或数据边界
- 决策与 [spec](../Acuven_Central_AI_Billing_Platform_Spec_v1.6.md) 的既有条款冲突（**偏离必须有 ADR**）
- 决策一旦落地，改回来的代价很高（表结构、加密方案、供应商绑定）
- 两个方案都说得通，选了其中一个，理由值得留给后来者

不写 ADR 的：实现细节、可逆的技术选型、纯风格问题。

## 格式

文件名 `ADR-<四位序号>-<英文 slug>.md`，序号只增不复用。固定六节：

```text
状态 / 背景 / 决策 / 备选方案 / 后果 / 收口条件
```

**「后果」一节必须写负面后果。** 只写好处的 ADR 没有价值——后来者需要知道当初知不知道代价、知道多少。

## 修订规则

「已生效的 ADR 不改内容」这条太粗，实际有三种情况，处理方式不同：

| 情况 | 怎么处理 |
| --- | --- |
| **勘误** —— 事实错误、论据算错、漏掉的硬约束 | **原地改**。正文里标注更正来源与日期，文件头「修订」一行追加记录 |
| **补完待定项** —— ADR 里显式写了「待定 / 选定后更新本节」的部分 | **原地补完**。同样在文件头「修订」一行追加记录 |
| **改变已生效的决策** | **写新 ADR**。旧的一字不改，只把「状态」改成 `已被 ADR-XXXX 取代` |

分开的理由：把勘误也逼去写新 ADR，会让一份含已知错误的文档永远留在原地，读的人未必会追到替代件；而允许决策被原地改写，批准记录就失去了绑定对象。**判据是「当初的决定变了没有」**——没变就是勘误或补完，变了才写新 ADR。

每次原地修订都必须在文件头加一行：

```text
| **修订** | 2026-09-10 勘误：<改了什么>（PR #N） |
```
