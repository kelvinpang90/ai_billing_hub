# ADR-0002 — 生产数据存储隔离：专用实例而非共享基建

## 背景

`E:\projects` 下的其他项目（`crm_os`、`erp_os`、`ai_search_os`、`demo_os`、`ai_chatbot_demo`、`rs-roof-pms`、`whatsapp_gateway`）都接入 `vps_infra` 提供的共享基建：

```text
infra_mysql   ← 各项目独立 db，同一个 MySQL 实例
infra_redis   ← 各项目独立 db 编号，同一个 Redis 实例
```

按这个惯例，本平台顺手接进去是最省事的做法：少一套容器、少一份运维、少占内存。

但本平台跑的是**钱包余额与不可变财务账本**，与其他项目不是同一类负载。spec §98 对此已有明确结论，[SPEC_REVIEW_v1.0.md](../SPEC_REVIEW_v1.0.md) 的 P2-23 也把这一点列为「要写进 spec 而不是留给实现者」的决定。

## 决策

**中心计费平台使用专用的 MySQL 与 Redis 容器**，不与现有应用共享实例。

按 spec §98，专用范围包括：

- 独立容器
- 独立凭据
- 独立数据库
- 独立持久卷
- 独立资源限制
- 独立备份任务

共享宿主网络或外部反向代理（`infra_nginx`）**允许**，但只能通过有文档的最小权限接口。

Integrated Application Backend **永不**直接连本平台数据库，只走认证 REST API + 签名 Webhook（§98、§2.1）。

## 备选方案

### A. 复用 `infra_mysql` / `infra_redis`

与 `E:\projects` 其他项目一致，省一套容器与运维。

**未采用**，三个理由：

1. **爆炸半径** —— 共享实例上任何一个项目的慢查询、连接耗尽、误操作 `DROP`、磁盘写满，都会波及钱包与账本。其他项目挂了是 demo 不可用；这里挂了是客户余额不可读、扣费停摆
2. **备份策略不同量级** —— §98.1 要求 RPO ≤ 5 分钟、binlog PITR、加密异地备份、季度恢复演练。把这套强度套到共享实例上，等于让所有项目陪跑；不套，则本平台达不到目标
3. **恢复语义冲突** —— 财务库的 PITR 恢复要精确到某个时间点。共享实例上做这件事会把其他项目一起拖回过去，实际上不可执行

### B. 独立 MySQL 实例但共享 Redis

Redis 只做队列与缓存，看起来风险低。

**未采用**。§98.1 明确要求「Redis / Celery 丢失不得摧毁持久化的财务、支付、通知、Webhook、文档生成工作」——这条靠的是数据库 outbox 可重建，不是 Redis 可靠。但共享 Redis 仍有两个问题：其他项目 `FLUSHALL` 或内存淘汰会打掉本平台的队列触发与重放保护缓存（§37 的 replay store），而且资源限制无法单独设。隔离成本很低，没有理由省。

## 后果

### 正面

- 故障域与其他项目切开，符合 §2.1「独立信任域与故障域」的整体设计
- §98.1 的 RPO/RTO、binlog PITR、恢复演练可以独立执行，不牵连其他项目
- 资源限制可按财务负载单独设定；容量规划不受其他项目影响
- 凭据独立，最小权限，泄露面更小

### 负面 —— 已知代价

- **单 VPS 上多跑一套 MySQL + Redis**，内存与磁盘开销增加。VPS 规格需要重新核算，Phase 0 的容量基线要把这部分算进去
- 多一份备份任务、监控项、升级维护面。§95 的监控清单要为这套单独配阈值与告警归属
- 与 `E:\projects` 其他项目的运维方式不一致，`playbooks` 里的共享基建部署流程对本项目**不适用**，需要单独的部署文档

### 需要注意

单 VPS 上「专用容器」隔离的是**逻辑故障域**，不是物理故障域。宿主机磁盘损坏、内核 panic、机器丢失仍然一起完蛋——这部分由 §98.1 的异地备份与 RTO ≤ 4 小时覆盖，不是本 ADR 的范围。

## 收口条件

- [ ] Phase 0 的 `docker-compose.yml` 含专用 `mysql` 与 `redis` 服务，独立卷与资源限制
- [ ] 备份任务只作用于本平台的卷与数据库
- [ ] 部署文档写明本项目**不接** `vps_infra` 的 `infra_mysql` / `infra_redis`
- [ ] VPS 容量核算把多出来的一套算进去
