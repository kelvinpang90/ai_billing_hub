## 背景

spec §112 要求上线前由 Acuven 批准一份数据治理政策：财务与个人数据不共用一条保留规则；财务记录在批准的保留期届满前不得自动清理；
不得以财务保留为由无限期保留联系人数据；个人数据不再需要时删除或不可逆匿名化；运营日志与导出要有明确的保留期、安全删除与容量上限。
§112.1 末段要求即使不做自助隐私请求界面，上线前也要有运营流程。

现状：

- 2026-09-13 决策 ⑤ 定了「财务记录先永久保存，运营日志暂定 30 天」，并写明个人数据的删除推迟到客户门户出现之后再定。门户（AIH-TASK-089..）、支付、收据、关户（AIH-TASK-209..215）现在都已上线。
- 库里除财务表外，有几张表**只增不减**、也没有清理任务：`refresh_tokens`、`password_reset_tokens`、`recovery_codes`、`domain_outbox`、`ai_usage_outbox`、`notifications`、钱包核对的两张表。
- 财务表与审计由 MySQL 触发器保证不可改、不可删（迁移 0006、0010、0017、0018、0035、0039 等）；用量事件的 `event_id` 唯一是「同一事件只扣一次」的唯一防线，而摄取对 `occurred_at` 没有过去的下限。
- 离机备份：每日全量与 binlog 35 天、月备份 366 天、**年备份永久**（2026-09-14）。
- 关户设计明确「关户不删除任何数据；个人数据的删除走另一流程」。

逐表盘点、个人数据位置与冲突清单在 `docs/data-governance.md` §3、§4、§11。

## 决策

### 1. 保留期总表

下表是 2026-11-23 的**批准值**（Kelvin 批准 `docs/data-governance.md` §10 的建议值，作为「补完待定项」原地修订）。K1 的 7 年待会计顾问核对，K4 与 K19–K22 的法律事实待法律顾问核对；顾问结论不同时按「收口条件」另写 ADR。

| --- | --- | --- | --- | --- |

### 2. 清理机制原则

所有清理任务（第 4 条）一律遵守：

1. **定时任务**：Celery Beat 每天一次，排在每日全量与日志外送之后的低峰时段。队列丢失只是少跑一轮（Invariant 14）。
2. **只删到期且已终结的行**：选择条件同时包含「终态」与「早于截止时刻」；删除按主键执行，`DELETE` 的 `WHERE` 里**重复**这两个条件。
   非终态（`PENDING`、`SENDING`、`HELD`、`RETRY`、`PROCESSING`、未复核等）一律不碰。
3. **批量上限**：每批按主键升序最多 1000 行、一个短事务；每轮每张表设总上限，超出的留到下一轮。不取钱包、租户行锁，不进入计费与支付的锁顺序。
4. **审计一条汇总**：每轮写一条审计（新动作，操作者为系统），`after_state` 只有每张表的截止时刻与删除行数，不含行内容；删除 0 行的表不写。
   匿名化另外逐个租户 / 用户写一条审计，只记对外 id 与字段名。
5. **不绕过数据库保证**：用运行账号执行；不 `TRUNCATE`、不 `DROP`、不删触发器、不关外键检查。外键或触发器拒绝即缺陷：本轮停止、错误日志、告警。
6. **开关与只数模式**：每个清理项独立开关、缺省关；先在生产「只数不删」跑一轮核对数字再打开。
7. **按规则、可重放**：条件只依赖行本身的状态与时间，备份恢复后下一轮自动重做。按请求提前做的匿名化另记库外登记表（只有租户 `public_id` 与日期），恢复后逐条重做。
8. **匿名化不可逆**：个人数据列换成固定占位值（非空列用满足约束的唯一不可投递值，可空列置空），不用可还原的哈希或加密；`tenants.company_name` 不动（已冻结在收据与对账单快照里）。

### 3. 财务记录与审计：V1 不清理

K1 与 K3 的到期清理不在本 ADR 实现。最早一批要到 2034 年 1 月才到期；而清理它们与现有保证直接冲突：

- `wallet_transactions` 的 DELETE 触发器（Invariant 5），以及钱包核对要求账本从序号 1 连续、从 0 链起；
- `usage_events.event_id` 是 Invariant 2、11 的唯一防线，删了以后同一事件可被再次扣费；
- `usage_event_conflicts`、`payment_receipts`、`audit_logs`、`fx_fetch_attempts` 的无条件触发器，`monthly_statements` 的定稿触发器，以及它们之间的 RESTRICT 外键。

2033 年内另写 ADR，给出期初结转、事件 id 墓碑（或摄取的时间下限）与按期限放行的触发器方案，并过设计闸门。在那之前这些表全部保留，等效于决策 ⑤ 的「永久」。

### 4. 之后要登记的清理任务

全部碰个人数据或删除行，**都需要设计闸门**，登记前按 CLAUDE.md 做预审；一个任务只做一层，`depends_on` 串起来：

| # | 任务 | 范围 |
| --- | --- | --- |
| R1 | 认证令牌清理（含清理框架） | Beat 条目、批量、开关、只数模式、审计汇总动作；`refresh_tokens`、`password_reset_tokens`、`recovery_codes` |
| R2 | 领域 outbox 清理 | `domain_outbox` 终态行；三类无处理器事件按 K10 选 a 保留，不清理 |
| R3 | AI 模块 outbox 清理 | `ai_usage_outbox` 终态行；改 AI-MODULE 设计「V1 不删」 |
| R4 | 关户后的个人数据处理 | 联系人匿名化、门户账号删除、停用管理员匿名化；管理端「提前匿名化」入口（数据主体删除请求用） |
| R5 | 通知与核对记录清理 | `notifications`、钱包核对运行与发现 |
| R7 | 审计 IP / UA（仅当 K3 选了缩短） | 迁移放开有限更新，或以后只写截断的 IP |

不走闸门的配套（R6）：R2 `yearly/` 加 lifecycle（管理员在控制台配）；runbook 新增「数据主体请求」「数据泄露」两节，「整台 VPS 没了」的恢复后对账加「重做提前匿名化」；
接入文档写明 `conversation_id` 不得含电话、邮箱等可识别值。

## 备选方案

- **全部永久保存（维持决策 ⑤）**：最简单，与所有触发器都不冲突。但联系人、门户账号、IP 无限期保留违反 spec §112 与 PDPA 的保留原则，上线闸门 Gate 2 过不了。不采用。
- **现在就实现财务记录的 7 年清理**：要改触发器、加期初结转与事件 id 墓碑，改动面覆盖账本、计费、摄取与核对，是全系统最高风险的一类迁移；而 8 年内没有一行到期。推迟（第 3 条）。
- **关户事务里同步删除个人数据**：关户会因为个人数据处理失败而失败，也失去了争议与退款期内联系客户的能力；而且关户后门户只读访问账单是已批准的行为。不采用，改为关户后按期处理。
- **用 MySQL 事件调度器或分区删除**：事件调度器绕过应用的审计与告警；按时间分区要重建大表、动外键。不采用，用应用内的定时任务。
- **匿名化用可还原的哈希或加密**：可还原就不是匿名化，仍属个人数据。不采用。

## 后果

- 负面：财务记录与审计实际上至少保留到 2034 年，审计里的 IP、UA，收据与对账单快照里的公司名（个体户即人名），以及 `PROCESSED` 用量事件里可能被接入方塞进去的个人数据，在这之前都**无法清除**。这是触发器与不变量的直接代价，K3、K23 是缓解办法。
- 负面：已匿名化的个人数据仍在离机备份里，直到备份过期；年备份改成 7 年之前就是永久。
- 负面：关户客户的门户账号在 K5 到期后删除，客户从此不能再在门户下载收据与对账单，要提前提醒客户自行保存；之后客户要这些单据，只能按 `docs/data-governance.md` §8 走访问请求，由管理员核实身份后交付。
- 负面：新增 5 个带闸门的任务和一个每日定时任务；清理写错的代价是删掉不该删的行，靠「条件重复写在 `DELETE` 里」「只数模式」「缺省关」三道兜住。
- 负面：三类无处理器的领域事件在 K10 选 a 时仍然永久留着。
- 正面：TODO 里「只增不减」两张表有了保留规则；上线闸门 Gate 2 有了可批准的对象；清理按规则执行，备份恢复后自动重做，不依赖人记得。
