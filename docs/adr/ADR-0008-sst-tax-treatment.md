## 背景

spec §45.1 是一道**闸门**，要求六项会计意见齐备才解锁生产环境的充值 / 收据 / 对账单 schema，并明写「**本规格不得自行发明税率**」。

六项里决策人只回答了一项：**费用含税**。

但这一项恰好是**唯一一项现在就必须知道的**——TODO 的 D2 写着「字段现在就要留，事后加等于重做所有历史凭证」。含税与不含税决定了 `payments.expected_amount`、`wallet_credit_amount` 与钱包余额这三个数**是毛额还是净额**，它是所有其它税务字段的解释基准。税率是多少、什么时候确认，可以等；这三个数是什么含义，不能等。

另有一处歧义必须先消除。「钱包额度含税」有两种读法：

- **(a)** 充值 RM100 → 钱包 +RM100，税嵌在**消费**时的单价里
- **(b)** 充值 RM100 → 先扣税，钱包 +RM92.xx

spec 第 359 行已经排除了 (b)：

> Any SST treatment, checkout total, and tax snapshot must follow the approved §45.1 policy and **must be shown explicitly rather than silently reducing wallet credit**.

「不得静默减少钱包额度」= 充值多少进多少。所以本 ADR 取 **(a)**。

## 决策

### 1. 所有对客户展示的金额都是含税价（tax-inclusive / 毛额）

具体到字段：

| 字段 | 含义 |
| --- | --- |
| `payments.expected_amount` | 客户实付的**含税**金额 |
| `payments.wallet_credit_amount` | 入钱包的金额，**等于** `expected_amount`（税不得静默扣减） |
| 钱包余额 | 含税余额 |
| 用量事件的计费金额（§80 算出的那个） | 含税单价算出的含税金额 |
| `payments.tax_amount` | 从毛额**反算**出的税额，用于收据展示；不参与钱包增减 |

**推论**：定价规则（`pricing_rules`）里配置的单价是**含税价**。这一条必须写进 Phase 2 的定价文档，否则运营按不含税录价，客户会被多收一个税。

### 2. 税额由毛额反算，且反算不得破坏「净 + 税 = 毛」

设税率 `r`（由 `tax_policy_versions.rate` 提供，本 ADR 不认定其值）：

```text
net_unrounded = gross / (1 + r)
net           = ROUND_HALF_UP(net_unrounded, 8)      # 只舍入这一次
tax           = gross - net                           # 相减得出，不独立舍入
```

**`tax` 必须由相减得出，不能独立算 `gross * r / (1 + r)` 再舍入。** 两个数各自舍入会让 `net + tax` 与 `gross` 差一个最小单位，而 `gross` 是已经入账的、不可变的账本金额——对不上就是收据与账本互相矛盾。

其余照 §80：中间值高精度 `Decimal`，持久化 `DECIMAL(20,8)`，展示 2 位。

### 3. 税率与确认时点不在本 ADR 定义

由 `tax_policy_versions` 承载（§74.9 已有 schema：`rate nullable`、`treatment_json`、`status`、`effective_from/to`）。闸门批准前该表**只能有 `DRAFT` 行**，`PUBLISHED` 是闸门的产物而不是前提。

### 4. 税率未定不阻塞 Phase 0–3

因为 `tax_policy_version_id` 与 `tax_amount` 都是 nullable（§74.7 已如此设计）。在税务政策发布前：

- 充值、钱包、用量计费**照常工作**，金额就是含税毛额
- 收据上的税额栏位留空，并显式标注「税务政策待定」，**不能显示 0**——0 是一个断言，空是一个事实
- 生产环境的充值按 §45.1 仍然阻塞，这不变

> 2026-10-17 补：第 5 节定了政策，这一节的过渡做法结束。收据不再留空税额栏、也不标「税务政策待定」，改按第 5 节。

### 5. spec §45.1 其余五项（2026-10-17 决策人拍板）

| §45.1 的问题 | 决定 | 对系统的含义 |
| --- | --- | --- |
| Acuven 是否已注册 / 是否需要注册 SST | **未注册，也不需要注册** | 不向客户收任何税；收据与对账单不印 SST 注册号 |
| AI 服务的税务分类与适用豁免 | **不适用**：未注册，不收税，分类用不上 | 系统里不记服务分类 |
| 充值属于储值、押金还是服务预付 | **服务预付** | 充值时不产生税务事件，与第 1 节「税不进钱包额度」一致；账本结构不变 |
| 税的确认时点与生效税率 / 版本 | **不适用**：价格是最终价，不拆税额、不设税率 | `tax_policy_versions` 的第一条 `PUBLISHED` 行：`rate` 为空，`treatment_json` 写明未注册、不收税；`payments.tax_amount` 恒为空，第 2 节的反算公式在未注册期间不执行 |
| receipt 与 statement 的强制字段 | **不出现任何税额栏**；印一句说明：「价格为最终价，已包含所有费用，不另收任何税费」（英文版：Prices are final and include all charges. No tax is charged separately.） | 收据与对账单的税额字段不展示；这句说明随税务政策版本快照进每张收据与对账单（Invariant 6），以后改措辞不改历史凭证 |

**为什么不写「费用包含 SST」**：决策人原先想在收据上写「费用包含 10% SST」，2026-10-17 改为上表的措辞。理由：未注册的公司在收据上声称包含 SST，等于对客户声称收了服务税；而且 10% 与服务税常见的 6% / 8% 税率对不上。给客户的 RM100 是最终价、供应商向 Acuven 收的税计入成本，这两件事用上面的措辞就能如实表达。

**什么时候要回头**：

- 应税营业额接近 SST 注册门槛，或 Acuven 决定自愿注册 —— 那时按注册时的实际税率写一条新的税务政策版本，收据改为正式的含税写法；第 1、2 节的含税口径与反算公式原样适用，历史凭证不改
- 聘请会计或税务顾问后，请其复核上表；对任何一项给出不同意见时（spec 1.9 §45.1 的要求）

## 备选方案

### A. 不含税（tax-exclusive）—— 未选

客户看到的价是净价，结账时另加税。

否定理由：与 spec 第 359 行直接冲突——不含税意味着充值 RM100 要么钱包只进 RM92.xx（静默减少额度），要么结账总额变成 RM108（那 `expected_amount` 与 `wallet_credit_amount` 就不相等，多一处对账面）。且本平台面向的是预付钱包模型，客户心智是「我充了多少就能用多少」，不含税会让余额与实际可用额度长期对不上。

### B. 等会计意见齐了再定字段语义 —— 未选

否定理由：D2 自己写着「字段现在就要留，事后加等于重做所有历史凭证」。毛额 / 净额是**解释基准**，不是可以补的字段——一旦有了历史充值记录再改口径，所有既往凭证的含义都要重新表述，而 Invariant 5 不允许改历史账本。

## 后果

### 正面

- Phase 0–3 不被税务闸门阻塞，钱包与计费可以照常开发
- 客户心智一致：充多少进多少，余额即可用额度
- `expected_amount == wallet_credit_amount` 恒等，少一处对账面

### 负面 —— 已知代价

- **税率变动直接吃掉毛利，而不是转嫁给客户。** 含税意味着客户价不变、净收入变。税率上调 1 个百分点，毛利就少那一个百分点——这必须由 markup 的缓冲吸收，与 [ADR-0005](ADR-0005-fx-rate-source.md) 里 FX 缓冲是同一类风险，且两者叠加
- **运营录价时必须录含税价。** 这是一个人为出错点，且错了不会报错，只会让客户被多收或少收。定价界面必须显式标注「含税」
- **若 Acuven 最终不需注册 SST**，历史凭证上「含税」的表述需要重新说明（税率为 0 与不适用是两件事）

### ⚠️ 未决项带来的风险

> 2026-10-17 补：第 5 节定了充值属于服务预付，所以下面第二种情形（储值、充值当刻确认税）不成立，`payments.tax_amount` 不进账本。但第一种情形里「消费时按含税价拆出税额确认」**在未注册期间也不执行**：Acuven 不收税，消费时不拆税额、不确认税，以第 5 节为准。将来注册后才按第一种情形拆税。

**税的确认时点尚未确定**，而它与「充值算储值 / 押金 / 服务预付」是同一个问题的两面：

- 若认定为**服务预付**：充值时不确认税，消费时按含税价拆出税额确认 —— 与本 ADR 的「税嵌在消费价里」自然吻合
- 若认定为**储值**：可能要求充值当刻就确认税 —— 那么 `payments.tax_amount` 就不只是收据展示字段，而要进账本，本 ADR 第 1 节的表要改

本 ADR 选「含税」这件事**倾向于**前者，但**不构成**会计认定。会计给出结论前，不得据此实现税额入账逻辑。

## 收口条件

spec §45.1 六项，逐条追踪：

- [x] 钱包额度含税还是不含税 —— **含税**（本 ADR）
- [x] Acuven 是否已注册 / 是否需要注册 SST —— 未注册、不需要注册（第 5 节，2026-10-17）
- [x] AI 服务的税务分类与适用豁免 —— 不适用（第 5 节）
- [x] 充值属于储值、押金还是服务预付 —— 服务预付（第 5 节）
- [x] 税的确认时点与生效税率 / 版本 —— 不适用，价格是最终价（第 5 节）
- [x] receipt 与 statement 的强制字段 —— 不出现税额栏，印「最终价、不另收税费」说明（第 5 节）
