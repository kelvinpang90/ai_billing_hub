## 背景

评审 R3 的担心：100 万条用量事件 = 100 万行 `wallet_transactions` + 100 万次钱包更新，而单笔金额可能只有 RM0.04。钱包变动按租户串行（§81 行锁、§82 明写「Celery 不消除这个串行要求」），最热的租户会不会成为瓶颈？要不要按对话或时间窗聚合成一行账本，明细只留在 `usage_events`？

现状（AIH-TASK-005 已上线）：

- 账本 `wallet_transactions` 有唯一约束 `(reference_type, reference_id)`：每个财务来源恰好一行。`AI_USAGE` 只能配 `reference_type = USAGE_EVENT`（CHECK 约束）。
- 钱包由账本插入触发器推进：每一行账本在钱包行锁内推进一次 `wallet_sequence`、更新一次余额。
- 还没有任何钱包 / 账本的吞吐实测。`docs/perf-baseline.md` 测的「写三张表 + 一次提交」在生产 VPS 上峰值约 308 次 / 秒，但那不是单行锁上的串行路径，不能直接当最热租户的上限。

### spec 对粒度的要求有多硬

聚合不是一个可以自由选择的实现细节，spec 在多处把「每个事件一行账本」写成了要求：

- §78：「Each financial source must have a unique effect constraint, **including one AI_USAGE debit per Usage Event**」
- §117：「**one immutable ledger row per usage**」
- §80：按事件舍入一次，并把「这个舍入后的事件金额」写进账本与钱包
- §9 / §111：请求级是计费的事实来源；「Do not replace request data with aggregates」
- 依赖逐事件追溯的下游：§19 rebill 要引用原账本交易与原金额；§62 reprocess 对单个事件预览新旧差额并生成账本调整；§46 晚到事件按 `processed_at` 进当期、要引用原用量期间；§70 客户钱包页的示例流水就是一行 `AI_USAGE -RM0.041200`。

### 量级

§119 的目标：稳态摄取 ≥ 20 事件 / 秒，5 分钟突发 ≥ 100 事件 / 秒，事件到扣款 p95 ≤ 60 秒，积压回补 ≥ 峰值的 5 倍。最坏情况是这些流量全部来自同一个租户。

- 串行路径上每个事件的锁持有时间 = 锁钱包 + 查重 + 锁租户 + 插一行账本（两个触发器）+ 标记事件已处理 + 提交。只要单次持锁在 10 毫秒以内，单个租户就能到 100 事件 / 秒；5 倍回补要 500 / 秒，即每次 2 毫秒以内。**提交时的刷盘是主要成本**，这正是下面方案 C 能削减的部分。
- 存储：100 万行账本（连索引）大约是几百 MB 的量级，MySQL 单表完全承受得起；§112 的留存策略决定长期增长。
- 这些是估算，不是实测。实测归 Phase 2 的 §119 压测（「最热租户」一项当前在 perf-baseline 里是 ❌）。

## 决策

**推荐方案 A**：每个用量事件一行 `AI_USAGE` 账本（即 2026-09-19 已同意的默认）。**方案 C 作为预案**：Phase 2 压测若最热租户达不到 §119，先改成「同一租户的多个事件在一个事务里各写一行」，仍然每事件一行，不改表结构、不偏离 spec。**方案 B 不采用。**

Phase 2 用量扣费的设计闸门必须包含：

1. 最热租户压测方案（单租户 100 事件 / 秒突发、500 / 秒回补、worker 重试与崩溃下事件状态 / 账本 / 余额一致，§117）
2. 压测不达标时切到方案 C 的判据与做法

## 备选方案

| 方案 | 做法 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 每事件一行，每事件一个事务**（推荐，现状） | worker 每处理一个事件：锁钱包 → 写一行 `USAGE_EVENT` 账本 → 标记事件已处理 → 提交 | 与 §78、§80、§117 的字面要求一致；唯一约束 `(USAGE_EVENT, event_id)` 直接在数据库层保证 Invariant 2 / 11；rebill、reprocess、晚到事件、钱包流水页都能一对一引用；已上线的表结构与触发器原样可用 | 每个事件一次提交，最热租户的吞吐受提交延迟限制；账本行数与事件数相同 | 推荐 |
| **B. 按对话或时间窗聚合**（新增 `reference_type = USAGE_WINDOW`，一个窗口一行） | 窗口结束时把窗口内事件的金额加总记一行，明细只留在 `usage_events` | 账本行数与钱包更新次数大幅减少 | **偏离 §78「one AI_USAGE debit per Usage Event」与 §117「one immutable ledger row per usage」**，要写偏离 ADR 并改 spec；唯一约束失去对象，「一个事件至多一次财务效果」要靠应用层保证；窗口开着的时候余额不反映已发生的用量，停机判定被推迟（加大透支，见 [ADR-0010](ADR-0010-suspension-threshold.md)）；晚到事件要决定并入哪个窗口；rebill / reprocess 要从窗口行拆回单事件金额；§80 的「按事件舍入一次后入账」与窗口加总之间多出一层舍入口径问题 | 不采用 |
| **C. 每事件一行，但同租户的多个事件批在一个事务里**（预案） | worker 一次取同一租户的 N 个待处理事件：锁一次钱包，逐个写 N 行账本（每行仍各自推进 `wallet_sequence`），一次提交 | 每事件一行的所有性质都保留，不改表结构；提交与加锁的成本摊到 N 个事件上，最热租户的吞吐大致按 N 倍提高 | 批内任何一个事件出错，要能单独隔离（不能让一个坏事件拖住整批）；一次提交里的事件越多，单个事件的扣款延迟分布越宽；跨越零点时要在批内正确触发跃迁（跃迁逻辑本来就是逐行的，但要测） | 预案：只在压测不达标时启用 |

## 后果

**好的**

- 账本与用量事件一对一，财务链路（§139「从 AI 请求到钱包交易与余额」）不需要任何拆分或推算。
- 已上线的唯一约束、CHECK 与触发器不用改；Phase 2 只写新的调用方。
- 性能出问题时有不改结构、不偏离 spec 的退路（方案 C）。

**坏的（必须知道的）**

- 最热租户的吞吐在 Phase 2 压测之前**没有实测数字**，本 ADR 只给了估算。
- 账本行数与事件数一样多，长期增长由 §112 的留存策略决定，而那项策略在上线闸门里还没批。
- 方案 C 如果启用，会让 worker 的错误隔离与重试逻辑复杂一截。
