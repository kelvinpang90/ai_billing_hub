# ADR-0007 — 并发 PENDING 支付：允许并存，都付都入账，用防误触窗口挡重复点击

| | |

| **状态** | 已接受 |

| **来源** | [REVIEW_FOLLOWUP_v1.1.md](../REVIEW_FOLLOWUP_v1.1.md) 的 R2。spec §42、§43 定义了充值与支付流程，但对「同一租户能否并存多笔 PENDING」无任何规定 |
| **影响** | `payments` 状态机、Phase 4 客户门户（spec §127）、spec §71 客户支付页 |

## 背景

客户在充值页连点两次，会产生两条 `payments` 记录、两次网关跳转。两笔都可能真的被支付。

spec 对此没有规定，于是有两个问题悬空：**能不能并存**，以及**两笔都付了怎么办**。

需要先把一件事分清楚：**重复创建**与**重复入账**是两个不同的问题。Invariant 3 管的是后者——同一笔支付不得入账两次。它并不要求禁止创建多笔支付。

## 决策

### 1. 允许同一租户并存多笔 PENDING 支付

### 2. 两笔都完成支付，就两笔都入账

各自产生一条 TOPUP 账本交易。

理由：**钱已经收到了。**拒绝入账等于吞客户的钱。而这是预付钱包，多充的部分仍然是客户的余额，不会造成损失——只是余额高于预期。

### 3. 防误触：60 秒内的同额重复请求复用同一笔

创建支付时，若该租户存在**金额相同**且创建于 **60 秒**内的 PENDING 支付，返回**既有那一笔**（同一 `payment_id`、同一跳转地址），不新建。

这是幂等复用，**不是拒绝**。它挡的是「手抖点两下」，不是「客户真的想充两次」。

### 4. PENDING 过期，但过期不是终态

PENDING 支付 60 分钟后由 Celery Beat 置为 `EXPIRED`（spec §43 已要求为选定的网关定义 `EXPIRED` 转换）。

⚠️ **过期之后若网关仍回调为已支付，仍然入账。**`EXPIRED` 只是给 UI 用的展示状态，不代表「这笔钱不要了」。收到的钱必须入账。

### 5. UI 显示待支付列表，不显示「当前那一笔」

R2 里问的「UI 显示哪一笔」是个伪问题——它假设了只能有一笔。列表形态下这个问题不存在。

### 6. 入账正确性不依赖并发控制

依赖的是 `(gateway, gateway_event_id)` 唯一约束（见 [ADR-0006](ADR-0006-payment-gateway-contract.md) 的 H1）加上 spec §81 的钱包按租户串行化。

这一条是本 ADR 成立的前提：**因为重复入账已经被唯一约束挡住了，所以才敢放开重复创建。**

## 备选方案

### A. 禁止并存，同一时刻只允许一笔 PENDING

否决理由有两条：

1. **会锁死客户。**客户开了一笔又不付也不取消，在超时之前就无法发起新的充值——包括金额不同的充值。这是用系统的整洁去换客户的可用性。
2. **它并不解决任何财务风险。**风险来自重复入账，而重复入账由唯一约束挡住，与创建了几笔无关。

### B. 允许并存但设上限（如 3 笔）

否决理由：上限值没有任何依据，而且超过上限时客户依然被锁死——只是把 A 的问题推后了几笔发生。

### C. 两笔都付时退掉其中一笔

否决理由：预付钱包里多充的钱仍是客户余额，退款平白多付一次网关手续费，还要一次人工操作。除非客户主动要求，否则退款是在制造工作量。

## 后果

### 正面

- 客户永远不会被自己未完成的订单锁死
- 「收到的钱一定入账」优先于「账面整洁」，与 Invariant 3 的方向一致
- 防重复入账的责任集中在一个地方（唯一约束），不分散到并发控制里

### 负面 —— 已知代价

- **客户确实可能充了两次**，余额高于预期。缓解手段只有 UI：明确显示待支付列表与最近入账记录。**人工退款流程超出 V1 范围，这是一个明确的缺口。**
- **60 秒与 60 分钟这两个数值是拍的**，没有真实数据支撑。上线后必须按实际的重复创建率复核。
- **`EXPIRED` 不是终态**，状态机比直觉复杂。实现时必须写明，并且要有测试覆盖「已过期的支付收到成功回调」这条路径——这正是最容易被漏掉的分支。
- 防误触窗口只比对金额与时间，**不比对客户意图**。客户在 60 秒内故意充两笔相同金额时，第二笔会被合并成第一笔。这是刻意的取舍：误触的概率远高于 60 秒内故意充两次同额。

## 收口条件

- Phase 4 实现时，60 秒防误触窗口与 60 分钟过期都做成配置项，不硬编码
- 必须有测试覆盖三条路径：并发创建两笔、两笔都支付成功、过期后收到支付成功回调
- 上线 1 个月后按真实数据复核这两个数值
- 人工退款流程在 V1 之后补，在此之前双充只能由人工介入处理
