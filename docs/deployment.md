## 2. 生产拓扑（§98、§99）

spec §99 钉死了形态：**单 VPS + Docker Compose，七个服务，没有独立的 staging**。
ADR-0002 钉死了隔离：**专用 MySQL 与 Redis 容器，不接 `vps_infra` 的共享实例**。

所以拓扑本身没有可选项，要定的是**它怎么接到那台机器已有的东西上**：

```text
Internet
  │
  ▼
infra_nginx（vps_infra，*.acuventech.com 通配符证书，已在跑）   ← 决策 ①
  │  least-privilege 接口，§98 允许但要求「documented」
  ▼
billing nginx（本项目，现在监听 80）
  ├── /            → frontend
  ├── /api/、/healthz → api
  └── /readyz      → api（仅私有网段）
        │
        ├── mysql（专用容器 + 专用卷）
        └── redis（专用容器 + 专用卷）
```

### ⚠️ 这个拓扑有一个后果，不是可选的

**如果走 `infra_nginx`（决策 ①ial 选 A），那么 `real_ip_header` + `set_real_ip_from`
不是「可以加」，是必须加**。否则本项目 nginx 看到的每个请求的对端都是
`infra_nginx`，于是：

- `limit_req`（`billing_auth`，10r/m）把**所有客户端算成同一个来源** —— 任何人打到
  第 21 个认证请求，**所有人**一起拿 429
- `/readyz` 的 `allow 10.0.0.0/8` 之类**形同虚设** —— 那层代理的地址本来就在私有网段里，
  于是等于对全网开放，而它的响应体逐个报出依赖状态
- 审计日志里的 `ip_address` 全是同一个值，取证时没用

应用侧已经准备好了（`app/core/clientip.py` + `BILLING_TRUSTED_PROXIES`，只在可信代理
后面才采信 `X-Forwarded-For`），**缺的就是边缘那一层**。三处一并收口。

## 3. 进程模型（T0.10 基线的直接输出）

现状：`Dockerfile` 的 CMD 是 `uvicorn app.main:app`，**没有 `--workers`**，也就是单进程。
T0.10 实测：**每一条路径都在并发 8 饱和**，机器有 20 核也用不上，多出来的并发全部
变成排队（写入路径 p99 从 37ms 到 1665ms）。

### ⚠️ 但「加 `--workers`」不是一个免费的开关

进程内那层兜底限流（`app/core/ratelimit.py` 的 `TokenBucket`）的状态在**进程内存**里。
跑 N 个 worker，同一个来源就有 N 个独立的桶 —— **兜底额度直接变成 N 倍**。

主控那层在边缘 nginx（`limit_req`），不受影响，所以这不是阻断项。但它意味着：
**调进程数的同时必须知道自己把兜底削弱了多少**，而不是事后才发现。

三条路，见决策 ②：

| | 做法 | 代价 |
| --- | --- | --- |
| A | 接受兜底被稀释，只依赖 nginx 那层 | 「不经 nginx 直连 uvicorn」这条路上的保护按 N 倍放宽 |
| B | 把每 worker 的额度除以 N | 要多一个「我是几个 worker 之一」的配置项，配错就是限流过严或过松，而且**错法是静默的** |
| C | 限流状态放 Redis | **已被 `ratelimit.py` 明确否决**：Redis 丢了会 fail-open，一个丢了就失效的安全控制比没有更危险 |

另外还有**内存**这条硬约束：Argon2 每次并发哈希要 **64 MiB**（T0.10 实测）。
N 个 worker × 并发登录数 × 64 MiB 是个能把单 VPS 吃光的量，定 worker 数时要一起算。

## 4. 边缘代理与 TLS

三件 T0.6 / T0.7 / T0.8a 欠下的，一并收口：

| 项 | 现状 | 要做成 |
| --- | --- | --- |
| 真实客户端地址 | 无 `real_ip` 配置 | `real_ip_header X-Forwarded-For` + `set_real_ip_from <上游地址>`；与应用侧 `BILLING_TRUSTED_PROXIES` 对齐 |
| 上游超时 | `proxy_connect_timeout` 挂着默认 **60 秒**；api 停机时实测要 **3.96 秒**才回 502 | 收到秒级。⚠️ 现状的后果是**一次停机在用户侧表现成「卡住」而不是「报错」**，而且每个挂起的请求都占着 nginx 一条连接 |
| TLS / 域名 | 只监听 80 | 由决策 ① 决定：走 `infra_nginx` 则 TLS 在那层终止，本层只收内网流量；独立则本层要自己管证书与续期 |
| nginx 运行用户 | 官方镜像默认（master 是 root） | 见决策 ④ |

## 5. 备份与恢复（§98.1）

spec 已经给了硬指标，**不是我们来定的**：

```text
RPO <= 5 minutes      —— 最多容忍丢 5 分钟的已提交数据
RTO <= 4 hours        —— 从「发现挂了」到「重新可用」不超过 4 小时
```

### 5.1 从指标反推出来的架构

**RPO ≤ 5 分钟**只有一种满足方式（§98.1 也点名了）：**全量备份 + binlog 的
point-in-time recovery**，而 binlog 必须**至少每 5 分钟**离机一次。

| 层 | 频率 | 去处 |
| --- | --- | --- |
| MySQL 全量（`mysqldump --single-transaction` 或 xtrabackup） | 每日一次 | 加密后离机 |
| MySQL binlog | **≤ 5 分钟一次**推送 | 加密后离机 |
| 不可变文档文件 | 变更后 | 离机，**独立访问控制** |
| 部署配置 | 变更后 | 离机 |
| **加密主密钥** | 轮换时 | ⚠️ **与数据库备份分开存放、两套访问控制**（ADR-0004 第 3 节） |

⚠️ **主密钥和数据库备份放在一起，等于两者都没有加密。**这一条是 ADR-0004 明写的，
也是最容易在「图省事，都塞进同一个桶」时破掉的。

**RTO ≤ 4 小时**要求恢复步骤是**演练过的**而不是写下来的。四小时看着宽，
但它要装下：发现 → 决策 → 起新主机 → 拉备份 → 解密 → 导入 → 重放 binlog →
核对 → 切流量。没演练过的流程，光「解密的密码在哪」就能吃掉一小时。

### 5.2 §98.1 要求而现在一件都没有的

- [ ] 备份成功与**新鲜度**的自动监控（§95 的 `backup age and backup failure`）
- [ ] **季度恢复演练**，且要验证钱包、账本、用量事件、支付、对账单、文档的完整性
- [ ] 书面的**灾难恢复顺序**与恢复后对账
- [ ] 保留期（与 §112 的财务保留期挂钩，见决策 ⑤）

⚠️ **「备份在跑」和「备份能恢复」是两件事。**只有第二件算数，而它只能靠演练证明。

### 5.3 恢复之后必须做的对账

INV-14 的设计（DB 是事实来源、Redis/Celery 只承载触发）在这里兑现：恢复之后
**不需要**重放队列，`domain_outbox` 里状态为 `PENDING` 的行会被周期恢复任务自然捡起。

⚠️ 但这意味着**恢复点之后已投递、却因回滚而重新变回 `PENDING` 的行会被重投**。
outbox 的投递语义本来就是 at-least-once，密码重置无害；**Phase 2 接上用量事件与
钱包之后，重投必须是幂等的** —— 那是 Phase 1/2 建表时的事，这里先记下依赖。

## 6. 加密密钥的宿主机那一半（ADR-0004）

应用侧 T0.8b 已经做完（信封加密、多版本钥匙串、文件注入）。**缺的全在宿主机上**：

- [ ] 主密钥文件 `chown 10001:10001` + `chmod 0400`
      （`10001` = `Dockerfile` 里的 `APP_UID`，T0.6 定的）
- [ ] ⚠️ **不得为了读密钥把容器改回 root** —— ADR-0004 明写
- [ ] runbook 写入主密钥恢复**流程**（脱敏），具体值进私有附录
- [ ] 季度恢复演练包含主密钥恢复

⚠️ **Compose 的 `file:` secret 走 bind mount，`uid`/`gid`/`mode` 三个选项只在 swarm
下生效、普通 compose 下被忽略** —— 宿主机文件的属主与权限原样带进容器。所以上面
那条 `chown` 不是建议，是唯一的生效途径。

⚠️ **还有一条 T0.8d 实测确认的**：文件不存在时 **`docker compose up` 照样起得来** ——
Docker 把缺失的 `file:` secret 挂成一个**空目录**，读它抛 `OSError`，于是密钥静默变成
空串。别指望 compose 替你挡住「忘了建文件」。

## 7. 生产日志（§94）

T0.3 做的是日志的**内容与格式**（结构化、request id、脱敏）。§94 还要求这些，
**全是部署侧的**：

| 要求 | 现状 | 缺口 |
| --- | --- | --- |
| 轮转 | compose 的 json-file driver 设了 `max-size: 10m` / `max-file: 3` | ⚠️ 那只是「堵住把开发机写满」，不是保留期策略 |
| 保留期 | 无 | 要与 §112 的分层保留期一致（见决策 ⑤） |
| 磁盘上限 | 只有每容器 30 MB 的隐含上限 | 要有主机层面的总量口径 |
| 安全删除 | 无 | §112 要求 |
| 异地留存 | 无 | 事故调查需要 |
| **磁盘告警** | 无 | ⚠️ §94 明写：**日志撑爆本地磁盘必须在威胁到 MySQL / 文档存储之前告警** |

## 8. 监控与告警（§95）

§95 列了 17 项指标，并要求**上线前每一项都有阈值、分级、通知对象、抑制规则和
runbook 链接**。现在**一项都没有**，因为没有任何日志聚合设施。

其中有一条是被点名钉住的：

> ⚠️ **`billing_readiness_degraded_redis`**（T0.5 派生，PR #28 审查指出）：
> `/readyz` 在 Redis 不可用时**刻意返回 200**（理由见 `app/core/config.py`：
> Redis 挂了就把 API 摘出轮转，恰好制造出 INV-1 要防的那种中断）。
> 代价是**负载均衡永远发现不了这个故障，它只能靠日志告警发现**。
> 告警落地之前，Redis 静默不可用是一个**已知的、被接受的检测缺口**。

另有一条 T0.6 派生的：

> ⚠️ **celery-beat 没有存活探针。**`celery inspect ping` 问的是 worker，够不着 beat。
> T0.8d 之后 beat 已经有了真实的周期任务（outbox 恢复），所以**它崩了就是静默故障**：
> outbox 不再补投、API 一切正常、没有任何报错。

## 9. ⚠️ 部署流水线：一条没有归属的 Phase 0 验收项

spec §123 的 Phase 0 验收写着：

```text
CI gates merge and deploys an immutable commit image
```

§99 进一步要求：合并到 `main` 触发 GitHub Actions 部署到 VPS、**不可变镜像标签对应
确切 commit**、按文档化的安全顺序跑迁移、等健康检查、跑冒烟测试、失败时有**演练过的**
回滚或前滚。

**现在 `.github/workflows/` 里只有 `ci.yml`，没有任何部署流水线。**
而 T0.1–T0.10 的任务描述里**没有一条认领它**。这是一个排序疏漏，不是取舍 ——
见决策 ⑥。

## 10. ⚠️ 需要拍板的六件事

下面每一条都会改变后面的具体做法。**没答案就往下做，做出来的要返工。**

### ① 本项目的 nginx 接在 `infra_nginx` 后面，还是自己面对公网？

| | 做法 | 影响 |
| --- | --- | --- |
| **A** | 走 `infra_nginx`（与其他七个项目一致，复用 `*.acuventech.com` 通配符证书） | TLS 在那层终止；**`real_ip_header` + `set_real_ip_from` 变成必须**；§98 要求把这个「least-privilege 接口」写成文档 |
| **B** | 独立监听 443，自己管证书 | 与 `vps_infra` 的惯例分岔；要自己做证书续期与告警；但少一跳，`$remote_addr` 天然就是真实客户端 |

倾向 **A**：与既有惯例一致，且 §98 明确允许（只要文档化）。但它把「限流按来源」
的正确性押在 `real_ip` 配对上，这一点要写进 runbook。

### ② API 跑几个 uvicorn worker，兜底限流怎么办？

见第 3 节的 A/B/C。倾向 **A**（接受兜底被稀释，主控在 nginx），因为 B 的错法是静默的、
C 已被否决。但 worker 数要和内存一起算：Argon2 每次并发哈希 64 MiB。

**前提是我不知道那台 VPS 的规格** —— 见 ③。

### ③ 那台 VPS 是什么规格？还剩多少余量？

几核、多少内存、磁盘多大、当前已经跑着八个项目占了多少。这个数直接决定：
worker 数、资源限制怎么设、日志与备份的磁盘预算、以及**这台机器到底装不装得下**。

⚠️ ADR-0002 的收口条件里就有一条「VPS 容量核算把多出来的一套算进去」，至今没算过。

### ④ nginx 容器要不要换成非 root 镜像？

现在是官方镜像默认（master 是 root，worker 是 `nginx` 用户）。换非 root 镜像要处理
绑定端口的问题。如果选了 ①A，本项目的 nginx 只收内网流量，风险面小很多 ——
**可能可以不换，但那要是个明确的决定，不是忘了做**。

### ⑤ 保留期定多少？

§112 要求**财务数据与个人数据不能共用一条保留规则**。要分别定：

- 不可变钱包 / 支付 / 对账单 / 审计记录 —— 法定保留期（马来西亚，多久？）
- 租户联系人等个人数据 —— 不再需要时删除或不可逆匿名化
- 运营日志 —— 明确保留期 + 安全删除 + 容量上限
- `password_reset_tokens` / `domain_outbox` —— 现在**只增不减，没有清理任务**

### ⑥ CD 是 T0.9 的一部分，还是单开一个编号？

它是 Phase 0 的验收项（§123），却没有任务认领。我的倾向是**单开 T0.11**：
T0.9 已经很大，而 CD 有自己的一套东西（镜像仓库、host secret、迁移顺序、
冒烟测试、回滚）。但这是你的排期，不是我的。

### ⑦ 备份放哪？

§98.1 要求「encrypted off-VPS backup storage」。要一个具体去处（S3 兼容对象存储？
另一台机器？哪家？），以及谁持有解密口令、放在哪里 —— ⚠️ **不能和主密钥同一处**。
