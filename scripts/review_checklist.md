# 审查清单

> 独立审查者（Codex 或 Claude Code，由 `scripts/codex-review.ps1 -Reviewer` 选）逐条走这份清单。流程见 [../docs/WORKFLOW.md](../docs/WORKFLOW.md)。
> 最后更新：2026-10-13

**这不是通用 code review 清单。** 通用问题（格式、命名、import 顺序、拼写）交给 linter 和 CI，不要在审查里重复。这份清单只盯**这个项目会亏钱、算错钱、泄露数据的地方**。

## 审查者守则

> 2026-10-13 从根目录 `AGENTS.md` 迁来：`AGENTS.md` 改成与 `CLAUDE.md` 同步的**实现者规则**（OpenClaw Worker 里 Codex 也可能当实现者）。
> 你的 CLI 在仓库里运行时仍会自动加载 `AGENTS.md` / `CLAUDE.md`；**本次你是审查者，那里让你写代码、提交、开 PR、回应审查的条款一律不适用**。
> 规则冲突时按这个顺序判断：本节「只读硬规则」→ [WORKFLOW.md](../docs/WORKFLOW.md) → 本清单其余各节 → Issue / PR 描述 → 代码与测试。

### 1. 只读硬规则（优先级最高）

- 不修改工作区任何文件（源代码、测试、文档都不改），不 `git add` / `commit` / `push`，不合并，不自行修复发现的问题
- 不自行调用 `gh` 发布 Review / Comment / Issue。发现问题写进最终审查意见，由实现者修改
- 唯一产出是**最后一条审查消息**；脚本负责落盘，并经 `scripts/gh_verified_write.py` 写入 PR / Issue 并回读验证
- 只读同时由机制强制：Codex 走 `codex exec -s read-only`，Claude Code 只开 Read / Grep / Glob

### 2. 目标与优先级

- 目标不是尽可能多找问题，而是**用最小必要上下文，找到真正可能影响生产的问题**。不要为了显得审查充分而制造意见
- 优先级：正确性 > 安全 > 数据一致性 > 回归 > 可靠性 > 可维护性 > 风格

### 3. 上下文预算

- 路径：审查材料 → diff → 改动文件 → 直接依赖 → 相关测试 → 必要的仓库搜索
- 只有为验证具体问题才读直接调用方 / 依赖；只有为验证行为才读测试；只有现有上下文不足以判断正确性才扩大搜索
- 默认不为「理解整个项目」扫描全仓库、不读全部历史代码与测试、不做与改动无关的架构探索；不重复读已验证且没变的代码
- **证据充分即停止。**满足以下条件就停：diff 已查、必要依赖已验证、相关测试已查或已跑、所有疑似阻断项已确认或排除、足以判断通过 / 拒绝。不要因为「也许别处还有问题」无边界搜索
- **高风险模块允许主动扩大上下文**（仍只读验证风险所必需的代码）：认证、授权、支付、计费、退款、钱包 / 余额、数据库迁移、数据库事务、安全敏感代码、共享核心模块、公开 API 契约、并发、Redis 锁、Celery 重试、幂等、外部金融 API。重点看事务边界、重复执行、重试、幂等、竞态、部分失败、数据一致性、授权、回归

### 4. 首审与复审

- 首审默认看：Issue / 需求、PR diff、改动文件、与改动直接相关的代码契约、相关测试。只有改动可能影响其他模块时才扩大范围
- 复审逐条走下面的 F 节。除非修复改变了设计或明显扩大影响面，不重新完整审整个 PR、不重查未变化且已验证的代码、不重做全仓库探索

### 5. 什么算意见、什么不报

- 正式意见要同时具备：具体位置、具体问题、合理触发路径、具体后果。说不出实际后果的不写
- 默认不报：格式、import 顺序、拼写、单纯命名或风格偏好、无实际后果的可读性建议、linter / formatter / CI 已能稳定发现的问题、没有合理触发路径的理论风险、与本次 diff 无关的历史问题
- **阻断项**包括但不限于：功能 bug、业务逻辑错误、安全漏洞、认证 / 授权错误、数据损坏或不一致、事务错误、明显回归、API 契约破坏、支付 / 计费错误、竞态、重复副作用、重要需求未实现
- **建议项**：有明确后果但风险较低的问题、有实际价值的重要测试缺口、明确的可靠性问题。不要大量输出低价值意见

### 6. 测试

- 先跑最相关的：改动功能的测试 → 模块测试 → 直接依赖的测试 → 必要时更广。默认不跑整个测试集；共享核心、数据库迁移、公开 API、跨模块、发布闸门或回归风险高时才考虑扩大
- 没跑就明说没跑；失败就明说失败；有跳过就不得声称「测试通过」
- **SQL 文本断言要与方言无关**：断言 SQL 文本处不得写死只在一种方言成立的字面量（SQLite 编译成 `JOIN`、MySQL 是 `INNER JOIN`；共享锁、标识符引号、分页写法也不同）。合格写法是只断言两种库相同的片段，或比较前先归一，只有 MySQL 才有的断言放在 `engine.dialect.name == "mysql"` 分支。发现了按建议项报，指出文件、行与方言差异。来由：Worker 沙箱跑不了 `tests.backend`，`[sqlite]` / `[mysql]` 参数化用例到 CI 的 MySQL 分片才第一次真跑，AIH-TASK-051 run `7fe4822e` 就挂在这里

### 7. 环境、高风险操作与沟通

- 环境是 PowerShell：不用 `wc` / `grep` / `head` / `tail` 这类 Unix 命令，优先 `git status` / `git diff --stat` / `git diff` / `git show` / `git log` 与 PowerShell 原生命令；命令失败不要连续换着试
- 以下操作失败一次就停止并汇报，禁止换参数连续重试：SSH / 远程登录、数据库连接、密码 / 凭据尝试、认证 / 授权连接测试、生产删除 / 重启 / 清空、防火墙 / fail2ban / 安全组修改。审查者的默认模式是「观察 + 验证 + 汇报」，不是「排障直到成功」
- 全部用中文；代码、标识符、API、技术术语可保留英文
- 材料有歧义时按 Issue / 需求 → PR 描述 → diff → 测试 → 现有代码契约判断；只有歧义直接影响通过 / 拒绝、且材料无法解决时才提出澄清。不得自行发明业务需求

## 审查类型

本清单服务两个闸门，先确认在审哪一个：

| 闸门 | 审什么 | 载体 | 判定 |
| --- | --- | --- | --- |
| **设计闸门** | 方案（还没有代码） | GitHub Issue，`design-gate` 标签 | `APPROVED: design v<N>` |
| **实现闸门** | 代码 diff | Pull Request | `VERDICT: APPROVE` |

设计闸门走下面的「设计审查」一节；实现闸门走后面的 A–E。

## 设计审查（只在审设计 Issue 时用）

对着 [.github/ISSUE_TEMPLATE/design-gate.md](../.github/ISSUE_TEMPLATE/design-gate.md) 的章节读，**明确回答这五个问题**，答不出来就是设计没写清楚：

1. **哪个具体场景会破坏不变量？** —— 要给出可复现的场景，不是「可能有风险」
2. **哪条失败路径没有定义最终状态或恢复方式？** —— 「捕获异常」不算最终状态
3. **哪项正确性只靠应用代码、缺少数据库约束？** —— 财务唯一性必须由数据库兜底，光靠应用层检查在并发下会漏
4. **哪个新增分支没有对应测试？** —— 特别是失败分支与边界值
5. **设计是否与 spec 的具体章节冲突？** —— 要点名章节号，不能只说「感觉不一致」

另外核对设计闸门的七条判定（见模板末尾）。任何一条不满足 → `REQUEST_CHANGES`。

**版本绑定**：`APPROVED: design v<N>` 的 `<N>` 按 Issue 正文末尾「版本绑定规则」核对——那一节随 Issue 进材料，此处不重复。

## 实现审查 —— 先看准入，再判断碰没碰钱

**准入**（脚本已在调你之前查过，材料里能看到结果）：CI 全绿；PR 正文小节齐全、`设计闸门：` 一行合法、`TODO 影响` 声明存在且与 diff 一致。准入不过的 PR 不会到你手上——如果材料显示准入信息缺失，那是脚本出了问题，**不要凑合审**。


先看 diff 涉及哪些区域，决定审查深度：

| 区域 | 深度 |
| --- | --- |
| 钱包 / 账本 / 定价 / 汇率 / 支付 / 幂等 / 状态机 | **全清单逐条走** |
| 用量摄取 / 认证与会话（集成侧与平台侧）/ Webhook | A + C + D |
| 前端 / 文档 / CI / 脚本 | D + E |
| 既不碰钱、也不碰用量摄取 / 认证与会话 / Webhook 的后端改动 | A + D + E |

⚠️ **区域看主题，不看「是不是 API」。**第四行覆盖骨架、健康检查、日志与错误处理、配置、依赖、迁移工具链这类改动。**新增一个端点本身不构成阻断理由**——PR 写「设计闸门：不适用」是否成立，看它碰了哪个主题，不看它有没有新端点。

## B. Definition of Done（spec §132）

功能类 PR 逐条核对，缺哪条就点名哪条：

1. 有数据库迁移
2. 有后端校验
3. 有鉴权
4. 该审计的地方有审计日志
5. 有测试
6. 有错误处理
7. API 契约有文档
8. 前端有 loading / error 状态
9. 租户隔离已验证
10. 该幂等的地方财务幂等已验证
11. 金额精度、版本选择、会计期间有对应测试
12. Redis / Celery 丢失后持久化作业能恢复
13. 迁移含生产锁表、备份、失败处理分析
14. 有监控、告警归属、runbook 覆盖
15. 量大的功能有性能与延迟目标验证

## C. 财务专项

这些是评审阶段真实踩过的坑，重点看：

- **精度**：中间值高精度，分量求和后**只舍入一次**到 MYR 8 位（spec §80）。有没有对每个 token 分量提前舍入
- **解析时点**：供应商价、汇率、客户定价规则**全部按 `occurred_at`**，不是摄取时间也不是处理时间（§16 / §17 / §82）
- **幂等顺序**：先 insert / upsert 再靠唯一约束冲突判定，**不能只靠读前检查**（§23 / §81）
- **归属校验**：`event_id` 冲突时比对 credential / tenant / project / payload 指纹，不匹配 → `IDEMPOTENCY_CONFLICT`，不是静默成功
- **钱包并发**：钱包变动在事务内 `SELECT ... FOR UPDATE`，且财务唯一性由数据库约束保证
- **不静默失败**：定价缺分量 → `PRICING_ERROR`，汇率缺失 → `FX_RATE_ERROR`，未知模型 → `MODEL_UNKNOWN`。**任何一处当零成本处理都是阻断项**（§15.1 / §16 / §83 / §84）
- **支付入账**：五个可信条件是否全查（签名、支付单已知且租户匹配、网关状态已付、金额完全一致、币种 MYR、该网关支付标识没入过账）。金额不符必须 `REVIEW_REQUIRED`，不许自动入账（§43）
- **状态单调**：状态跃迁递增 `status_version`，消费端只应用更大的版本（§24 / §28 / §30）
- **期间归属**：用量期按 `occurred_at`，入账期按 `processed_at`，晚到走 `PRIOR_PERIOD_ADJUSTMENT`（§46）

## D. 通用但关键

- **密钥**：签名密钥必须可逆加密存储（HMAC 需要明文），**不是单向 hash**；日志 / 审计 / API 响应 / 异常栈都不许出现明文（§36）
- **仓库是公开的**：有没有提交凭据、`.env`、真实主机名 / IP、客户数据、供应商合同价（主机名只有 `docs/adr/ADR-0001-repository-visibility.md` 派生要求里登记的两处例外）
- **测试覆盖了改动引入的边界吗** —— 不是「有测试」，是「有覆盖这次改动新引入的分支和边界」
- **错误路径**：失败分支有没有留下半提交状态
- **`REQ-*` 追溯**：碰了关键需求的 PR，描述里有没有引用对应的 `REQ-*` ID（[REQUIREMENTS.md](../docs/REQUIREMENTS.md) 第一节）

## E. 文档 / CI / 脚本类 PR

- 文档改动有没有和 spec 冲突（spec 是唯一事实来源，导航层不得另立说法）
- 链接与 `§N` 引用是否有效（CI 的 `docs` job 会查，但它查不出**语义**上指错章节）
- CI 改动会不会让某个检查形同虚设（比如加了 `continue-on-error`、`|| true`）

## F. 复审（材料里有「复审上下文」时）

材料会带上轮审查、Claude 的回应、以及本轮相对上轮的增量统计与 diff（增量 = 两版「PR 相对 base 的 diff」之间的差异，同步 base 带进来的改动不计入）。逐条做：

- **上轮每条意见都有交代吗** —— 回应表里缺一条 = 阻断（沉默跳过）
- **「已修」真的修好了吗** —— 证据里的 `SHA · 文件:行` 脚本已确认存在，但存在 ≠ 修好。到那一行看一眼是不是真的解决了指出的后果
- **增量 diff 只含修复吗** —— 与上轮意见无关的改动一律指出；范围扩张必须在回应里有必要性说明，没有 = 阻断。#5 六轮不收敛就是每轮都顺手加了新东西
- **「不改」的理由站得住吗** —— 引的 spec 章节 / 不变量是否真的支持那个理由
- 第三轮起：回应里有没有 `### 完整影响面`；有的话它列的范围与增量 diff 对得上吗
- 回应里的 `SHA · 文件:行` 只证明引用存在；为修一条意见改了大量无关代码，按上面「增量 diff 只含修复吗」判断是否阻断

## G. 登记 PR、收尾 PR 与任务记录

- **登记 PR**（把任务登记或改成 `ready`）按下面几条核对，不满足的作为阻断项指出（完整说明在控制面仓库 `docs/ONBOARD-PROJECT.md`「登记任务之前」）：
  - `title` 是一句说明这一项做什么的中文：80 个字符以内、一行、首尾无空白；不含反引号、尖括号、「」『』【】〖〗，不带 emoji、链接、路径、主机名
  - 按条件预审：任务有设计闸门（碰钱、碰个人数据、状态机、改数据库结构或迁移），或 `contract_check` 对它给出拆分 WARN、预计改动接近约 1500 行时，登记 PR 必须贴出 `python -m worker.design_precheck`（控制面仓库）的完整输出；`NOT_READY` 的每条发现要么已修掉，要么在 PR 里逐条写明为什么不成立。不满足条件的任务，登记 PR 里有一行「预审：不适用」并给出理由
  - 拆分：一个任务只做一层（数据库 / 业务规则 / 接口 / 前端），用 `depends_on` 串起来，每层合并后都能单独通过检查与 CI；规则多的设计先交付规则和对应测试再接接口；`allowed_change_paths` 超过 12 个、验收标准超过 8 条、或预计改动超过约 1500 行要先拆，拆不开要在登记 PR 里写明原因；预审报出的 `SCOPE_GAP` 先改契约
  - 有用户可见页面的前端任务按 `CLAUDE.md`「登记任务时的浏览器验收约定」带 acceptance 块
- **收尾 PR** 由 OpenClaw 自动开、CI 通过后自动合并、不触发部署，正常不经过审查。只有自动收尾失败、由人手工开收尾 PR 时才会到你手上：它只能含两处机械改动——`.platform/tasks.yaml` 里这个任务 `status: ready` 改成 `status: done`，从 `docs/TODO.md` planning-v1 的「当前计划」删掉这一项（其后序号减一）；超出的内容作为阻断项指出
- **任务记录**写在 PR 描述的「改了什么」「如何验证」「已知未做 / 留给后续」里（2026-09-30 起），不要求 `docs/TODO.md` 有记录段，也不要求 `.platform/README.md` 状态句或 `docs/REVIEW-LOG.md` 交付行。设计文件或任务契约里写「记进 `docs/TODO.md`」的内容同样以 PR 描述为准。PR 在 `docs/TODO.md` 新增记录段，或改了勾选项与规划块以外的内容，作为建议项指出

## 输出纪律

- **阻断项**只留：破坏不变量、会算错钱、会泄露数据、会静默失败的问题
- **建议项**留：可读性、可维护性、更简洁的写法
- 指不出「具体位置 + 具体后果」的，不要写
- 没有问题就写「无」，**不要为了显得认真而凑数**
- 只要有一条阻断项，`VERDICT` 必须是 `REQUEST_CHANGES`，不得出现「有严重问题，但整体通过」
- **输出格式不在本清单定义**，由 `scripts/codex-review.ps1` 的提示词给定，照它写；判定行必须是**最后一行**，后面不得再有任何文字（脚本解析最后一行决定退出码）
- 格式归提示词管，**内容底线归这里管**：每条意见都要能答出位置（具体到 `文件:行`）、问题、触发条件、后果、建议（最小必要修复方向）。不要直接实现修复
- 先给结论再给意见；最终输出只留结论、证据、影响、必要建议与判定，不输出冗长的思考过程
