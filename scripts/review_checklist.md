# 审查清单

> Codex 独立审查时逐条走这份清单。流程见 [../docs/WORKFLOW.md](../docs/WORKFLOW.md)。
> 最后更新：2026-09-11

**这不是通用 code review 清单。** 通用问题（格式、命名、import 顺序、拼写）交给 linter 和 CI，不要在审查里重复。这份清单只盯**这个项目会亏钱、算错钱、泄露数据的地方**。

---

## 审查类型

本清单服务两个闸门，先确认在审哪一个：

| 闸门 | 审什么 | 载体 | 判定 |
| --- | --- | --- | --- |
| **设计闸门** | 方案（还没有代码） | GitHub Issue，`design-gate` 标签 | `APPROVED: design v<N>` |
| **实现闸门** | 代码 diff | Pull Request | `VERDICT: APPROVE` |

设计闸门走下面的「设计审查」一节；实现闸门走后面的 A–E。

---

## 设计审查（只在审设计 Issue 时用）

对着 [.github/ISSUE_TEMPLATE/design-gate.md](../.github/ISSUE_TEMPLATE/design-gate.md) 的章节读，**明确回答这五个问题**，答不出来就是设计没写清楚：

1. **哪个具体场景会破坏不变量？** —— 要给出可复现的场景，不是「可能有风险」
2. **哪条失败路径没有定义最终状态或恢复方式？** —— 「捕获异常」不算最终状态
3. **哪项正确性只靠应用代码、缺少数据库约束？** —— 财务唯一性必须由数据库兜底，光靠应用层检查在并发下会漏
4. **哪个新增分支没有对应测试？** —— 特别是失败分支与边界值
5. **设计是否与 spec 的具体章节冲突？** —— 要点名章节号，不能只说「感觉不一致」

另外核对设计闸门的七条判定（见模板末尾）。任何一条不满足 → `REQUEST_CHANGES`。

**版本绑定**：`APPROVED: design v<N>` 的 `<N>` 按 Issue 正文末尾「版本绑定规则」核对——那一节随 Issue 进材料，此处不重复。

## 实现审查 —— 先看准入，再判断碰没碰钱

**准入**（脚本已在调你之前查过，材料里能看到结果）：CI 全绿；PR 正文小节齐全、`设计闸门：` 一行合法、`TODO 影响` 声明存在且与 diff 一致。准入不过的 PR 不会到你手上——如果材料显示准入信息缺失，那是脚本出了问题，**不要凑合审**。


先看 diff 涉及哪些区域，决定审查深度：

| 区域 | 深度 |
| --- | --- |
| 钱包 / 账本 / 定价 / 汇率 / 支付 / 幂等 / 状态机 | **全清单逐条走** |
| 用量摄取 / 集成认证 / Webhook | A + C + D |
| 前端 / 文档 / CI / 脚本 | D + E |
| 既不碰钱、也不碰用量摄取 / 集成认证 / Webhook 的后端改动 | A + D + E |

⚠️ **区域看主题，不看「是不是 API」。**第四行覆盖骨架、健康检查、日志与错误处理、配置、依赖、迁移工具链这类改动。**新增一个端点本身不构成阻断理由**——PR 写「设计闸门：不适用」是否成立，看它碰了哪个主题，不看它有没有新端点。

## A. 14 条不变量

**正文不在这里。** 打开 [ARCHITECTURE.md 第 6 节](../docs/ARCHITECTURE.md)（权威英文版是 spec §133）对照着看——同一张清单只留一份，两份迟早分叉，而分叉那一刻两边都不会报错（见 [REVIEW-LOG](../docs/REVIEW-LOG.md)）。

逐条问「这个改动有没有可能破坏它」。**任何一条被破坏 = 阻断项。**

下表只管**怎么查**，编号与 ARCHITECTURE 第 6 节一一对应：

| # | 这条怎么查 |
| --- | --- |
| 1 | 计费侧超时 / 报错 / 整个不可用时，客户的 AI 请求还能不能正常返回？有没有把计费调用放进 AI 响应的同步路径 |
| 2 | 重放同一个 `event_id` 会不会产生第二笔扣费？挡住它的是数据库唯一约束，还是只有读前检查 |
| 3 | 网关重发同一个回调会不会二次入账？`(gateway, gateway_event_id)` 的唯一约束在不在 |
| 4 | 有没有直接 UPDATE 余额的路径 |
| 5 | 有没有 UPDATE / DELETE 打到历史行 |
| 6 | 新增或改动的写入路径有没有漏存某一项快照（供应商价、定价规则、汇率、源币种金额、MYR 换算） |
| 7 | 客户侧 API / 页面有没有漏出 `provider_cost` / `markup` / `margin` |
| 8 | 每个查询是否都带 tenant 过滤 |
| 9 | 有没有把 prompt / response 写进任何表或日志 |
| 10 | 有没有 `float` |
| 11 | `event_id` 复用且归属指纹不匹配时，判的是冲突还是「重复成功」？必须是冲突 |
| 12 | 有没有能改已定稿对账单的路径？晚到与跨期数据是不是走了开放期间的显式调整 |
| 13 | 钱包变动、状态跃迁、审计记录、出站领域事件是不是在**同一个事务**里？有没有先提交再补发事件 |
| 14 | 队列被清空后，这条流程能不能只靠数据库状态重建？有没有哪个状态只存在于 Redis / Celery 里 |

## B. Definition of Done（spec §132）

功能类 PR 逐条核对，缺哪条就点名哪条：

1. 有数据库迁移
2. 有后端校验
3. 有鉴权
4. 该审计的地方有审计日志
5. 有测试
6. 有错误处理
7. API 契约有文档
8. 前端有 loading / error 状态
9. 租户隔离已验证
10. 该幂等的地方财务幂等已验证
11. 金额精度、版本选择、会计期间有对应测试
12. Redis / Celery 丢失后持久化作业能恢复
13. 迁移含生产锁表、备份、失败处理分析
14. 有监控、告警归属、runbook 覆盖
15. 量大的功能有性能与延迟目标验证

## C. 财务专项

这些是评审阶段真实踩过的坑，重点看：

- **精度**：中间值高精度，分量求和后**只舍入一次**到 MYR 8 位（spec §80）。有没有对每个 token 分量提前舍入
- **解析时点**：供应商价、汇率、客户定价规则**全部按 `occurred_at`**，不是摄取时间也不是处理时间（§16 / §17 / §82）
- **幂等顺序**：先 insert / upsert 再靠唯一约束冲突判定，**不能只靠读前检查**（§23 / §81）
- **归属校验**：`event_id` 冲突时比对 credential / tenant / project / payload 指纹，不匹配 → `IDEMPOTENCY_CONFLICT`，不是静默成功
- **钱包并发**：钱包变动在事务内 `SELECT ... FOR UPDATE`，且财务唯一性由数据库约束保证
- **不静默失败**：定价缺分量 → `PRICING_ERROR`，汇率缺失 → `FX_RATE_ERROR`，未知模型 → `MODEL_UNKNOWN`。**任何一处当零成本处理都是阻断项**（§15.1 / §16 / §83 / §84）
- **支付入账**：五个可信条件是否全查（签名、支付单已知且租户匹配、网关状态已付、金额完全一致、币种 MYR、该网关支付标识没入过账）。金额不符必须 `REVIEW_REQUIRED`，不许自动入账（§43）
- **状态单调**：状态跃迁递增 `status_version`，消费端只应用更大的版本（§24 / §28 / §30）
- **期间归属**：用量期按 `occurred_at`，入账期按 `processed_at`，晚到走 `PRIOR_PERIOD_ADJUSTMENT`（§46）

## D. 通用但关键

- **密钥**：签名密钥必须可逆加密存储（HMAC 需要明文），**不是单向 hash**；日志 / 审计 / API 响应 / 异常栈都不许出现明文（§36）
- **仓库是公开的**：有没有提交凭据、`.env`、真实主机名 / IP、客户数据、供应商合同价
- **测试覆盖了改动引入的边界吗** —— 不是「有测试」，是「有覆盖这次改动新引入的分支和边界」
- **错误路径**：失败分支有没有留下半提交状态
- **`REQ-*` 追溯**：碰了关键需求的 PR，描述里有没有引用对应的 `REQ-*` ID（[REQUIREMENTS.md](../docs/REQUIREMENTS.md) 第一节）

## E. 文档 / CI / 脚本类 PR

- 文档改动有没有和 spec 冲突（spec 是唯一事实来源，导航层不得另立说法）
- 链接与 `§N` 引用是否有效（CI 的 `docs` job 会查，但它查不出**语义**上指错章节）
- CI 改动会不会让某个检查形同虚设（比如加了 `continue-on-error`、`|| true`）

## F. 复审（材料里有「复审上下文」时）

材料会带上轮审查、Claude 的回应、以及本轮相对上轮的增量统计与 diff（增量 = 两版「PR 相对 base 的 diff」之间的差异，同步 base 带进来的改动不计入）。逐条做：

- **上轮每条意见都有交代吗** —— 回应表里缺一条 = 阻断（沉默跳过）
- **「已修」真的修好了吗** —— 证据里的 `SHA · 文件:行` 脚本已确认存在，但存在 ≠ 修好。到那一行看一眼是不是真的解决了指出的后果
- **增量 diff 只含修复吗** —— 与上轮意见无关的改动一律指出；范围扩张必须在回应里有必要性说明，没有 = 阻断。#5 六轮不收敛就是每轮都顺手加了新东西
- **「不改」的理由站得住吗** —— 引的 spec 章节 / 不变量是否真的支持那个理由
- 第三轮起：回应里有没有 `### 完整影响面`；有的话它列的范围与增量 diff 对得上吗

## 输出纪律

- **阻断项**只留：破坏不变量、会算错钱、会泄露数据、会静默失败的问题
- **建议项**留：可读性、可维护性、更简洁的写法
- 指不出「具体位置 + 具体后果」的，不要写
- 没有问题就写「无」，**不要为了显得认真而凑数**
- 只要有一条阻断项，`VERDICT` 必须是 `REQUEST_CHANGES`
